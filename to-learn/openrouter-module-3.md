# OpenRouter, модуль 3: роутинг, надёжность, структурированный вывод

Часть плана [openrouter-plan.md](openrouter-plan.md). Неделя

- [ ] Занятие 7. Фолбэки моделей и автовыбор

## Зачем этот модуль

До сих пор OpenRouter использовался как «тот же OpenAI, только адрес
другой». Здесь появляется то, чего у прямого API нет: одна и та же
модель у нескольких провайдеров, автоматический перезапуск при отказе,
цепочка запасных моделей. Для продуктового менеджера это про
надёжность сервиса, а не про удобство разработчика.

## Занятие 7. Фолбэки моделей и автовыбор

**Теория (25 мин).**
[Провайдерская маршрутизация](https://openrouter.ai/docs/guides/routing/provider-selection).
Ключевое различие, которое надо усвоить: **отказ провайдера
обрабатывается автоматически, а запасные модели это то, что включаешь
сам**. Цепочка задаётся массивом `models`. Есть `openrouter/auto`,
который выбирает модель сам.

**Практика (35 мин):**

1. Сделать вызов с массивом `models`: основная модель плюс две
   запасные. По умолчанию сначала перебираются все эндпоинты основной
   модели, и только потом идёт следующая модель в списке
2. Подставить первой заведомо недоступную модель и убедиться, что
   запрос дошёл до второй
3. Прогнать одну задачу через `openrouter/auto` и посмотреть в ответе,
   какую модель он выбрал
4. Записать вывод: годится ли автовыбор для задачи с эталоном из ДЗ4
   или он ломает воспроизводимость замера

**Проверка:** можешь объяснить разницу между отказом провайдера и
фолбэком модели, и почему первое включено по умолчанию, а второе нет.

## Занятие 8. Провайдеры, приоритеты и отказоустойчивость

**Теория (20 мин).** Одна и та же модель бывает у нескольких
провайдеров с разной ценой, задержкой и надёжностью. Поле `sort` в
настройках провайдера задаёт приоритет по одному признаку и при этом
выключает балансировку нагрузки, то есть провайдеры перебираются строго
по порядку.

**Практика (40 мин):**

1. В каталоге найти модель, доступную у нескольких провайдеров,
   сравнить их цены и задержки
2. Сделать один и тот же запрос трижды подряд и посмотреть, один и тот
   же провайдер отвечает или разные
3. Зафиксировать провайдера через настройки и убедиться, что теперь
   отвечает только он
4. Отсортировать по цене, затем по задержке, сравнить фактические
   результаты. Записать: насколько разница между провайдерами вообще
   значима на этой задаче, или это шум

**Проверка:** умеешь зафиксировать конкретного провайдера и объяснить,
зачем это нужно при замере.

## Занятие 9. Структурированный вывод и вызов инструментов

**Теория (25 мин).** Через единый API доступны вызов инструментов,
структурированный вывод, потоковая передача, кеширование промптов и
токены рассуждений. Важная оговорка: это не свойства OpenRouter, а
свойства моделей под ним, поэтому поддержка отличается от модели к
модели, и это видно в карточке модели.

**Практика (35 мин):**

1. Повторить задачу строгого JSON из ДЗ4, но через штатный
   структурированный вывод вместо инструкции в промпте. Сравнить долю
   валидного JSON с результатом из модуля 1
2. Проверить это на модели-кандидате, у которой в карточке заявлен
   структурированный вывод, и на модели, у которой не заявлен
3. Сверить с выводом 1 из [DECISIONS_LOG.md](../DECISIONS_LOG.md):
   ограничение в промпте это не техническая гарантия. Проверить, меняет
   ли штатный структурированный вывод эту картину, или запрет всё равно
   обходится
4. Один вызов с инструментом, по образцу ДЗ11 на Agno, чтобы увидеть
   формат вызова через единый API

**Проверка:** есть цифры, показывающие, даёт ли штатный
структурированный вывод преимущество перед инструкцией в промпте на
этой конкретной задаче.

## Что должно получиться к концу модуля

1. Рабочая цепочка запасных моделей и понимание, когда она нужна
2. Умение зафиксировать провайдера ради воспроизводимости замера
3. Замер: структурированный вывод против инструкции в промпте
4. Четвёртая независимая проверка вывода 1 из `DECISIONS_LOG.md`
