# Тема 3. Контейнеризація ML-моделей (Docker)

Вступ
Вітаємо в третій темі курсу MLOps!

Ця тема - про те, як ML-модель перетворюється з «файлу, що працює на ноутбуці інженера» на delivery-артефакт, який можна стабільно й передбачувано запускати будь-де. Для AI Project Manager контейнеризація - це не написання Dockerfile вручну, а розуміння процесу: що потрапляє в Docker-image, навіщо, які артефакти має підготувати команда, які питання поставити інженерам, як перевірити готовність до deployment і які ризики виникають перед production.

Цілі навчання:

💼 Що ви зможете після теми:

Розуміти, чому контейнеризація - обов'язковий крок production ML, а не «DevOps-мода», і пояснювати її бізнес-наслідки: time-to-market, reproducibility, вартість зберігання й delivery.
Правильно ставити задачу команді на контейнеризацію та формулювати acceptance criteria.
Перевіряти готовність Docker-image як delivery-артефакту (build, run, формат I/O, версія моделі, README, security).
Оцінювати оптимізацію образу за вимірюваними метриками (розмір, час збірки, security findings), не змінюючи поведінку моделі.
Бачити весь контур ML-сервісу (модель + API + база + кеш) і розуміти роль Docker Compose у delivery.
Складати risk register і доносити стан delivery до нетехнічних стейкхолдерів.
Технічні фрагменти коду в темі наведено довідково - щоб AI PM розумів логіку. Писати їх самостійно не потрібно.


Один із перших практичних кроків у бік продакшену - контейнеризація. Почнемо? 🚀
Що таке контейнеризація та навіщо вона потрібна
💡	Контейнеризація - спосіб запакувати застосунок (у нашому випадку ML-модель) разом з усіма залежностями, бібліотеками й середовищем в один ізольований блок - контейнер, який працює однаково незалежно від ОС, версії Python чи встановлених пакетів.





CI (Continuous Integration) - практика, коли зміни в коді часто додаються до спільного репозиторію й автоматично перевіряються (збірка, тести, лінтери), щоб швидко знаходити помилки.

Чому це критично для ML? Уявіть ситуацію: локально все працює → у CI тест падає через відсутній пакет → у проді інша версія numpy, і модель дає дивні результати. Контейнер дозволяє зробити «скриншот середовища», який запускається як на сервері, так і в хмарі, так і на ноутбуці.

Стандарт індустрії - Docker. Він зручний для локальної підготовки й перевірки контейнерів; Kubernetes потім керує запуском і масштабуванням великої кількості таких контейнерів на серверах або в хмарі. Тобто Docker готує контейнерний артефакт, а Kubernetes - запускає його у складнішій інфраструктурі.



Контейнер vs віртуальна машина - коротко для AI PM




Згенеровано ШІ



Віртуальна машина містить повноцінну гостьову ОС: повна ізоляція, але багато ресурсів і повільний старт.



Контейнер розділяє ядро хост-системи: запускається за секунди, легший, дешевший. Для ML-сервісів, CI/CD і хмари це робить контейнери практичним вибором за замовчуванням.



📎	Бізнес-сенс.
Контейнеризація прибирає клас проблем «працює тільки на моєму ноутбуці», що прямо впливає на швидкість і передбачуваність релізів.
Загальні підходи до контейнеризації моделей
У технічних прикладах Docker-image створюється через код: модель, inference-скрипт, залежності, Dockerfile і запуск контейнера. Для AI PM важливо дивитися на цей процес не як на написання Dockerfile, а як на підготовку ML-моделі до стабільного запуску в реальному середовищі.

AI PM має розуміти: що саме потрапляє в Docker-image; навіщо модель контейнеризують; які артефакти готує ML/AI-команда; які питання поставити інженерам; як перевірити готовність до deployment; які ризики можливі перед production.

📎	Контейнеризація - це перехід від «на ноутбуці ML-інженера модель працює» до «модель можна однаково запустити на сервері, у CI/CD, у Kubernetes або в хмарі».


Docker-image часто стає одиницею delivery для ML-рішення. Формула проста:

ML-модель + inference-код + залежності + системне середовище = Docker-image



Що має входити в Docker-image ML-моделі

Компонент	Навіщо потрібен
Файл моделі	Основний ML-артефакт, що виконує передбачення.
Inference-код	Завантажує модель і запускає передбачення.
Python-залежності	torch, tensorflow, scikit-learn, pandas, numpy.
Системні залежності	Linux-пакети для роботи бібліотек.
Конфігурації	Параметри запуску, шляхи, змінні середовища.
Команда запуску	Що виконується при старті контейнера.


AI PM перевіряє, що всі ці частини враховані в задачі, а не залишені «десь локально».
Спрощена структура ML-проєкту (для розуміння)
ml-service/
├── app/inference.py     # код для запуску моделі
├── model/model.pt       # файл моделі
├── requirements.txt     # Python-залежності
├── Dockerfile           # інструкція для створення image
└── test_input.jpg       # тестовий приклад



код + модель + залежності + Dockerfile = готовий Docker-image



10 кроків контролю контейнеризації очима AI PM



КРОК 1. Визначити, для чого створюється Docker-image.

Сценарії бувають різні: локальний запуск, тестування в CI/CD, batch-обробка, API-сервіс, deployment у Kubernetes, демонстрація замовнику. Приклад постановки: «Підготувати Docker-image для моделі класифікації зображень, який запускає inference через CLI і приймає шлях до зображення». Принципово:

контейнер для CLI, batch-job і API організовується по-різному.



КРОК 2. Визначити ML-артефакт.

Який саме файл моделі фінальний (model.pt, model.pkl, model.onnx, saved_model/)?

Питання до команди: Який формат? Чи потрібен оригінальний Python-клас моделі? Окремі ваги? конфіг? версія? чи можна відтворити inference без training-коду? На яких даних і для якої задачі модель створена? Для production модель - це контрольований артефакт із версією (image-classifier:v1.0.0, fraud-detector:v2.3.1).



КРОК 3. Визначити формат входу й виходу.

AI PM фіксує: що подається на вхід, у якому форматі, що повертається, як обробляються помилки. Приклади - зображення → ID/назва класу + confidence; CSV → CSV із прогнозами; JSON-запит → JSON із prediction, confidence, model_version. Інакше frontend, backend, data engineering і ML-команда розумітимуть роботу моделі по-різному.



КРОК 4. Перевірити залежності.

Якщо версії не зафіксовані, модель може працювати в одного інженера й ламатися в контейнері. AI PM контролює: зафіксовані ключові версії; сумісність з Python; враховані CPU/GPU-залежності; немає зайвих важких бібліотек; перевірені ліцензії; описано, як оновлювати. Погано: torch / numpy / pandas. Краще: torch==2.7.0 / numpy==2.2.5 / pandas==2.2.3.



КРОК 5. Розуміти Dockerfile (не писати). Достатньо читати основні рядки:

Рядок	Що означає
FROM python:3.13-slim	Базовий образ із Python.
WORKDIR /app	Робоча папка в контейнері.
COPY requirements.txt .	Копіювання списку залежностей.
RUN pip install ...	Встановлення бібліотек.
COPY app/ /app/	Inference-код.
COPY model/ /app/model/	Файл моделі.
ENTRYPOINT ...	Команда запуску.


Головне питання AI PM: чи містить Docker-image усе необхідне для запуску без ручного налаштування середовища?


КРОК 6. Зібрати образ - зрозуміла назва й версія.

Погано: docker build -t test .. Краще: docker build -t image-classifier:1.0.0 .. Ще краще для команди: registry.company.com/ml/image-classifier:1.0.0 - таку назву легше використовувати в CI/CD, Kubernetes і документації.



КРОК 7. Перевірити локальний запуск з погляду delivery.

Очікуваний результат містить prediction, class_id, confidence, model_version. AI PM перевіряє: контейнер запускається без ручних дій; модель завантажується без помилок; вхід обробляється; відповідь у очікуваному форматі; є версія моделі; помилки зрозумілі й не ламають процес мовчки.



КРОК 8. Зафіксувати acceptance criteria.

Образ готовий, якщо: успішно збирається docker build; запускається docker run без ручного встановлення залежностей; модель завантажується; приймає тестовий input у погодженому форматі; повертає prediction у погодженому форматі; у відповіді/логах є версія моделі; помилки обробляються зрозуміло; розмір не перевищує погоджений ліміт; залежності зафіксовані; інструкція запуску є в README.



КРОК 9. Перевірити ризики перед deployment.

Ризик	Що може піти не так	Що перевірити
Невідповідність середовища	Працює локально, не в контейнері.	docker run локально.
Нефіксовані залежності	Нова версія бібліотеки ламає inference.	Версії в requirements.txt.
Великий image	Повільний deployment, зайве сховище.	Розмір образу.
Немає версії моделі	Незрозуміло, яка модель дала prediction.	model_version.
Немає логів	Складно діагностувати.	Структуровані логи.
Немає тестового input / README	Неможливо швидко перевірити або запустити.	Тестовий приклад, інструкція.
Неправильний формат виходу	Backend/frontend не можуть використати результат.	Узгоджений контракт.


КРОК 10. Передати образ у delivery pipeline.

Типовий шлях: локальна збірка → registry → CI/CD → staging → production. AI PM відстежує не лише факт створення образу, а й весь шлях артефакту до реального запуску.



Приклад задачі для команди та user story

Підготувати Docker-image для моделі класифікації зображень. Image має містити файл моделі, inference-код, Python- і системні залежності, команду запуску. Контейнер: запускається через docker run; приймає шлях до зображення; повертає prediction у тексті/JSON; містить версію моделі; має README. Acceptance: docker build успішний; docker run працює на тестовому зображенні; результат у погодженому форматі; залежності зафіксовані; зрозуміла назва й версія; придатний для CI/CD або staging.


As an AI Project Manager,
I want the ML model to be packaged into a Docker-image,
so that the team can run inference consistently across local, staging, and production.

Acceptance criteria:
Given a trained ML model, when the Docker image is built and run,
then the container loads the model, processes a valid input, and returns a prediction in the agreed format.






📎	Головна роль AI PM - не писати Dockerfile, а забезпечити, щоб команда чітко визначила модель, формат I/O, залежності, критерії готовності, ризики та шлях образу до deployment.
Оптимізація Docker-image - погляд AI PM
На попередньому етапі команда створила робочий Docker-image для запуску ML-моделі.



❗ Оптимізований образ виконує ту саму задачу, але ефективніше: менший розмір; лише runtime-залежності; без зайвих build-інструментів; швидше передається й збирається; менша attack surface; легше проходить security scan.

☝	Якщо контейнер працює локально - це ще не означає, що він оптимальний для delivery.
Напрям	Що означає	Чому важливо для AI PM
Зменшення розміру	Прибрати зайві залежності, кеші, тимчасові файли.	Швидше завантажується в registry, staging і production.
Безпека	Прибрати dev/build-утиліти.	Менше вразливостей перед релізом.
Кешування	Правильна структура шарів.	CI/CD працює швидше.
Швидкість запуску	Мінімальний runtime.	Контейнер швидше стартує в production.
Відтворюваність	Фіксація версій.	Менше ризику, що модель зламається після оновлення.
Підтримуваність	Зрозуміла структура + документація.	Інші команди легше підтримують deployment.


Multi-stage build простими словами: у першій «кімнаті» команда збирає всі матеріали (build-інструменти, залежності), а у фінальний контейнер потрапляє лише готовий результат - модель, inference-код, мінімальні runtime-залежності, без інструментів і «сміття».



Що AI PM має перевірити перед оптимізацією

Перед тим як ставити задачу на оптимізацію Docker-image, AI PM має уточнити:

1. Для чого використовується image: локальний запуск, staging, production, batch-job чи API?
2. Чи потрібен GPU runtime?
3. Який поточний розмір image?
4. Скільки часу займає docker build?
5. Скільки часу займає запуск контейнера?
6. Чи проходить image security scan?
7. Чи є зайві залежності?
8. Чи зафіксовані версії бібліотек?
9. Чи потрібні всі файли, які копіюються в image?
10. Чи є окремі training-файли, які не потрібні для inference?



Ці питання допомагають відрізнити реальну оптимізацію від формального «переписування Dockerfile».



Оптимізація має бути вимірюваною. AI PM бажано просити команду не просто повідомити, що image оптимізовано, а надати конкретні метрики.

Метрика	Приклад до оптимізації	Приклад після оптимізації
Розмір Docker-image	1.8 GB	650 MB
Час збірки	9 хв	4 хв
Час запуску контейнера	12 с	5 с
Кількість security findings	28	8
Кількість шарів	18	11
Час pull у staging	2 хв	40 с


Такі метрики допомагають AI PM оцінити результат не суб’єктивно, а через вимірювані показники.



Ризики надмірної оптимізації

Оптимізація не повинна ламати функціональність ML-моделі.

Іноді команда може занадто агресивно зменшувати Docker-image і випадково прибрати залежності, які потрібні для inference.

Можливі ризики:

модель перестає завантажуватися;
preprocessing працює інакше;
зникають потрібні системні бібліотеки;
inference результат змінюється;
контейнер працює локально, але не працює в Kubernetes;
складність Dockerfile зростає настільки, що його важко підтримувати.
Тому AI PM має зафіксувати головний принцип:

Оптимізація не повинна змінювати поведінку моделі.



Спочатку перевіряється коректність inference, і лише потім оцінюється розмір, швидкість та безпека.



Що має бути в результаті задачі

Після оптимізації команда має передати не просто новий Dockerfile, а зрозумілий набір артефактів:

1. Оновлений Dockerfile.
2. Оновлений requirements.txt або lock-файл.
3. Зібраний Docker-image з версією.
4. Інструкцію запуску.
5. Порівняння image до / після оптимізації.
6. Результат тестового inference.
7. Результат security scan або короткий звіт.
8. Коментар щодо залишкових ризиків.



Це дозволяє AI PM зрозуміти, що задача завершена не формально, а з урахуванням delivery-процесу.



Приклад короткої user story

As an AI Project Manager,
I want the ML Docker-image to be optimized,
so that the model can be deployed faster, more securely, and with lower infrastructure overhead.



Acceptance criteria:

Given a working Docker-image for an ML model,
when the image is optimized,
then it should keep the same inference behavior while reducing unnecessary size, dependencies, and security risks.



Приклад формулювання в Jira / таск-трекері

Title:
Optimize Docker image for ML model inference

Description:
The current Docker image successfully runs ML inference but may contain unnecessary dependencies and have a large size. The goal is to optimize the image for staging/production usage without changing inference behavior.

Scope:
- Review current Dockerfile.
- Remove unnecessary build/dev dependencies from the final image.
- Improve layer caching.
- Use an appropriate lightweight base image.
- Keep only files required for inference.
- Verify that inference output remains unchanged.
- Provide before/after metrics.

Acceptance criteria:
- docker build succeeds.
- docker run succeeds on the test input.
- Inference output is consistent with the previous image.
- Image size is reduced or justified.
- No critical vulnerabilities remain unresolved.
- README is updated with build and run commands.
- Before/after comparison is attached to the task.



Docker Compose - погляд AI PM

ML-модель рідко працює сама. Реальна система: Frontend/Backend → Model API → ML-модель → PostgreSQL / Redis / Logs / Monitoring. AI PM має бачити весь контур, а не лише модель.

Docker Compose відповідає на питання: як запустити всі частини ML-системи разом однією командою? Це не повноцінна production-оркестрація (це робота Kubernetes), але добре підходить для: локального запуску сервісу; демонстрації замовнику; перевірки інтеграції API↔модель↔база↔кеш; onboarding нового розробника; інтеграційного тестування перед deployment; підготовки до перенесення в Kubernetes.



Спрощений приклад (довідково):

services:
  model-api:
    build: .
    ports: ["8000:8000"]
    volumes: ["./model:/app/model:ro"]
    environment: ["MODEL_PATH=/app/model/model.pt"]



Для AI PM важлива не кожна YAML-деталь, а те, що цей файл формалізує правила запуску ML-сервісу: Dockerfile описує один сервіс, Compose-файл - систему з кількох сервісів. Що контролювати: чи описані всі залежні сервіси (а не запускаються вручну); чи немає production-секретів у Compose-файлі; чи не підключається локальний стенд до production-бази/черги.

Для AI PM оптимізація Docker-image для ML-моделей - це не про ручне написання Dockerfile, а про керування якістю delivery-артефакту.



Оптимізований Docker-image допомагає:

швидше доставляти модель у staging і production;
зменшити витрати на зберігання та передачу image;
знизити кількість вразливостей;
прискорити CI/CD pipeline;
зробити запуск inference більш стабільним;
спростити підтримку ML-рішення.
Головна задача AI PM - переконатися, що оптимізація має вимірюваний результат і не змінює поведінку моделі. Тобто контейнер після оптимізації має запускати той самий inference, але бути меншим, чистішим, безпечнішим і зручнішим для deployment.
Docker Compose. Як керувати моделлю в одному середовищі
У попередніх підтемах ML-модель була запакована в Docker-контейнер. Це означає, що модель уже можна запускати як окремий відтворюваний артефакт.

Але в реальному AI/ML-проєкті модель майже ніколи не працює ізольовано. Вона зазвичай є частиною більшої системи, де поруч із нею працюють API, база даних, кеш, черга повідомлень, сервіс логування або моніторинг.

Наприклад, ML-рішення може складатися з таких компонентів:

model-api - сервіс, який приймає HTTP-запити й запускає inference;
ML-модель - файл або артефакт, який виконує передбачення;
Redis - кеш або черга для тимчасового зберігання запитів;
PostgreSQL - база даних для логування результатів;
frontend або backend - зовнішній застосунок, який звертається до ML API;
monitoring/logging - сервіси для спостереження за роботою моделі.
З погляду AI PM важливо розуміти: після контейнеризації моделі команда переходить від задачі «запустити модель» до задачі «запустити ML-систему».

Окремий контейнер з моделлю ≠ готова ML-система



Готова ML-система має кілька пов’язаних сервісів, які повинні запускатися разом, бачити один одного в мережі, мати правильні змінні середовища, порти, залежності та інструкції для локального тестування.



Навіщо тут потрібен Docker Compose

Якщо запускати кожен контейнер вручну, процес швидко стає незручним. Окремо потрібно запустити API, окремо Redis, окремо базу даних, окремо налаштувати мережу, порти, змінні середовища та порядок запуску.



Для локальної розробки, демонстрацій, інтеграційного тестування й невеликих стендів часто використовують Docker Compose.

⚙	Docker Compose - це інструмент, який дозволяє керувати кількома пов’язаними контейнерами за допомогою одного YAML-файлу.


Офіційна документація Docker описує Compose як інструмент для визначення й запуску multi-container applications; він дозволяє описати сервіси, мережі та volumes в одному YAML-файлі й запустити весь application stack однією командою.



Для сучасного Docker Compose V2 використовується команда:

docker compose up



Саме ця команда створює, запускає й підключає сервіси, описані у Compose-

файлі. За потреби запуск у фоновому режимі виконується через docker compose up -d.



Що має розуміти AI PM

AI PM не обов’язково має самостійно писати compose.yaml або docker-compose.yml, але має розуміти його роль у delivery-процесі.

Docker Compose відповідає на питання:

Як запустити всі частини ML-системи разом однією командою?



Для AI PM це важливо, тому що Compose-файл часто стає основою для:

локального запуску ML-сервісу;
швидкої демонстрації замовнику;
перевірки інтеграції між API, моделлю, базою та кешем;
onboarding нового розробника;
інтеграційного тестування перед deployment;
підготовки до перенесення системи в Kubernetes або хмарне середовище.
Docker Compose не замінює повноцінну production-оркестрацію на рівні Kubernetes, але добре підходить для локального запуску й перевірки взаємодії сервісів.



Acceptance criteria

Задачу з Docker Compose можна вважати завершеною, якщо:

1. У репозиторії є Compose-файл для локального запуску ML-системи.
2. Система запускається однією командою docker compose up.
3. model-api доступний на погодженому порту.
4. endpoint /health підтверджує, що сервіс і модель готові.
5. endpoint /predict повертає prediction на тестовому input.
6. Усі необхідні залежні сервіси описані в Compose-файлі.
7. Конфігурації винесені в environment або .env.
8. У Compose-файлі немає production-секретів.
9. README містить інструкцію запуску й перевірки.
10. Команда може пояснити, як цей локальний стенд пов’язаний із майбутнім staging або production deployment.

Як час збірки впливає на бізнес

Контейнеризація сповільнює CI/CD: збирати ML-образ із PyTorch і CUDA може займати від 5 до 30 хвилин. Це прямий вплив на бізнес-показники.

Метрика	Вплив від повільної збірки
Time-to-deploy hotfix	30-хвилинна збірка → інцидент тримається 30+ хв довше → SLA-штраф.
Developer velocity	Інженер чекає замість кодити → ~10 хвилин/коміт × 10 комітів/день = 1.5 год/день втрачено.
CI cost	Self-hosted runner = окремий instance; managed CI (GitLab/GitHub Actions) = $/хв.
Experimental velocity	DS не може швидко тестувати ідеї в проді → менше експериментів на квартал.
Incident response	P0/P1 інцидент → fix + повна перезбірка → 40+ хв замість 10.


Що зменшує час збірки:

Multi-stage build - розділяє build-етап і runtime-етап, щоб у фінальний image потрапляли лише потрібні артефакти.
Layer caching у CI - повторне використання вже зібраних Docker layers або BuildKit cache, щоб не перевстановлювати важкі залежності при кожній зміні коду.
Pre-built base images з ML-залежностями - команда один раз готує базовий image з важкими залежностями, а прикладні сервіси перевикористовують його в наступних збірках.
BuildKit + remote cache - експорт та імпорт build cache через registry або інший підтримуваний backend, щоб CI/CD не починав кожну збірку з нуля.
Compute scaling - швидші CI runners можуть скоротити час CPU-bound build, якщо bottleneck справді в обчисленнях, а не в мережі або registry.
Docker BuildKit підтримує експорт build cache у зовнішні backends і його повторне використання в наступних збірках, тому це коректніше описувати як build cache, а не як «S3 layer» або «cache mount» без уточнення механізму.



Як PM-у розуміти, що час збірки став проблемою:

Build-time на сторінці dashboard CI/CD - постійно > 10 хв і росте.
Скарги команди «довго чекаю на pipeline».
Cost report показує великі рахунки за CI Compute.
Hotfix-and-deploy цикл > 30 хв.
