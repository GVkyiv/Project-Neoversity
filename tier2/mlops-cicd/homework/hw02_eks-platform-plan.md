# Архітектурно-управлінський план EKS-платформи для AI/ML-продукту

Цей документ визначає структуру платформи Kubernetes (Amazon EKS) для розміщення сервісу машинного навчання. План охоплює поділ середовищ, стратегію кластерів, профілі навантажень, керування обчислювальними ресурсами, політики безпеки та критерії готовності до промислової експлуатації.

---

## 1. Середовища

Для забезпечення безперебійної роботи продукту формуються три ізольовані середовища:

1. **dev (розробка та експерименти)**:
   - Призначення: перевірка гіпотез, первинна інтеграція коду, налагодження сервісів інференсу та тест нових конфігурацій контейнерів.
   - Особливості: допускаються збої, швидкі перезапуски, використання недорогих переривчастих ресурсів (Spot-інстансів).

2. **staging (передпромислове тестування)**:
   - Призначення: валідація кандидатів у реліз, регресійне тестування, оцінка точності та затримки нових моделей на знеособлених даних, навантажувальне тестування.
   - Особливості: конфігурація та налаштування мережі повністю дублюють промислове середовище.

3. **prod (промислова експлуатація)**:
   - Призначення: обробка реальних запитів клієнтів з дотриманням угод про рівень сервісу (SLA/SLO).
   - Особливості: висока доступність, географічна надлишковість у кількох зонах доступності, суворий контроль змін.

**Чому неприпустимо запускати всі навантаження без ізоляції:**
Відсутність меж між середовищами створює загрозу, коли експериментальна модель у dev споживає всю доступну пам'ять або квоту графічних процесорів, спричиняючи відмову промислового API (ефект «гучного сусіда»). Крім того, спільний простір підвищує ризик витоку конфіденційних клієнтських даних у тестові логи та унеможливлює суворе розмежування прав доступу.

## 2. Стратегія кластерів та просторів імен

**Обраний підхід: комбінована дворівнева стратегія (два EKS-кластери):**
- **Кластер non-prod:** містить середовища `dev` та `staging`, розділені за допомогою просторів імен (namespaces).
- **Кластер prod:** виділений незалежний кластер виключно для промислового середовища.

**Обґрунтування вибору:**
- **Безпека та ізоляція:** промисловий кластер повністю ізольовано на рівні віртуальної хмари (VPC) та площини управління (control plane). Помилка конфігурації у тестовому середовищі технічно не може зашкодити промисловому трафіку.
- **Оптимізація вартості:** об'єднання dev і staging в один non-prod кластер заощаджує витрати на оплату фіксованої вартості площини управління EKS (control plane fee) та дозволяє спільно використовувати системні інструменти моніторингу й CI/CD агентів.
- **Складність підтримки:** супроводжувати два кластери значно простіше, ніж підтримувати три незалежні системи, водночас це знімає ризики випадкових деструктивних дій у prod.
- **Мінімізація ризиків:** гарантується відсутність впливу пікових навантажень тестування на живих користувачів.

## 3. Робочі навантаження (Workloads)

Платформа забезпечує виконання чотирьох типів навантажень:

| Навантаження | Опис та профіль роботи | Тип ресурсу (CPU / GPU) |
|---|---|---|
| **Inference API** | Сервіс обробки запитів користувачів у реальному часі. Вимагає низької латентності та горизонтального масштабування (HPA). | **CPU** (інстанси c6i/c7i) для оптимізованих моделей (ONNX, OpenVINO, квантовані моделі). **GPU** підключається лише за потреби для важких мовних моделей. |
| **Batch jobs** | Періодична пакетна обробка даних, генерація ембеддингів для каталогу, офлайн-розрахунок скорингу. Працюють за розкладом або подіями. | **CPU** для підготовки даних; можливий короткостроковий запуск **GPU** для масової генерації ембеддингів великими мережами. |
| **Monitoring & Logging** | Системні компоненти спостережуваності: Prometheus, Grafana, OpenTelemetry, FluentBit. Постійне базове навантаження. | **Виключно CPU** (інстанси загального призначення m6i/t3). |
| **Testing & Heavy Inference** | Оцінка нових великих моделей та періодична донавчальна адаптація на staging/dev. | **GPU** (виділені вузли з картами Nvidia A10G або T4). |

---

## 4. Планування груп вузлів (Node Groups)

Поділ груп вузлів на CPU та GPU є фундаментальною вимогою ефективної архітектури.

1. **CPU Node Groups:**
   - Завдання: веб-сервери, мікросервіси API, сервіси моніторингу, більшість завдань пакетної обробки.
   - Архітектура: масштабовані групи вузлів (Auto Scaling Groups) у кількох зонах доступності. Використовуються стандартні інстанси та Spot-інстанси для фонових черг.

2. **GPU Node Groups:**
   - Завдання: виконання важких математичних тензорних обчислень, де продуктивність паралельних ядер GPU забезпечує необхідну швидкість відгуку або обробки великих батчів.
   - Механізм ізоляції: використання міток (labels), обмежень (taints: `sku=gpu:NoSchedule`) та дозволів (tolerations), щоб звичайні CPU-поди випадково не займали дорогі графічні інстанси.

3. **Керування витратами та масштабування GPU:**
   - Вартість GPU-інстансів у 5-10 разів перевищує вартість аналогічних CPU-вузлів. Тримати GPU-ноди постійно увімкненими без навантаження: прямий витік бюджету.
   - Рішення: налаштування Karpenter або Cluster Autoscaler на автоматичне зведення кількості GPU-нод до нуля (scale-to-zero), коли в черзі немає завдань із відповідними tolerations. Запуск нод відбувається динамічно під час появи відповідного поду.

## 5. Управління платформою (Governance)

### Матриця доступів та ролі (RBAC)
- **dev:** розробники та інженери даних мають повний доступ на створення й редагування ресурсів у межах свого простору імен.
- **staging:** автоматизований деплой через CI/CD конвеєр; розробники мають доступ рівня Read-Only для перегляду логів і діагностики.
- **prod:** нульовий прямий доступ людей (zero standing access). Усі зміни вносяться виключно автоматизованими сервісними акаунтами через GitOps/CI/CD. Доступ інженерів SRE можливий лише через механізм тимчасових привілеїв під час критичних інцидентів (break-glass).

### Квоти ресурсів (ResourceQuotas та LimitRanges)
Для кожного простору імен обов'язково встановлюються:
- Ліміти на сумарне споживання CPU та оперативної пам'яті (ResourceQuota).
- Обмеження на максимальну кількість запитуваних GPU (наприклад, не більше 2 одиниць у просторі dev).
- Обов'язкове завдання параметрів `requests` та `limits` для кожного поду (LimitRange), що запобігає виснаженню пам'яті на рівні фізичної ноди.

### Розподіл відповідальності (Ownership)
- **Платформна команда / MLOps:** життєвий цикл кластерів EKS, конфігурація контролерів, мережі, сховищ, драйверів Nvidia, операторів автоскейлінгу та безпека інфраструктури.
- **ML-інженери:** якість роботи моделі, ефективність контейнера інференсу, оптимізація розміру моделі, коректність роботи API.
- **Команда продукту / Product Manager:** бізнес-метрики сервісу, погодження цільового бюджету, визначення вимог до доступності та допустимої вартості одного запиту.

## 6. Спостережуваність та перевірка готовності (Production-Readiness)

### Ключові метрики контролю
- **Латентність:** час обробки запиту інференсу (p50, p95, p99).
- **Рівень помилок:** частка відповідей HTTP 5xx та внутрішніх помилок контейнера моделі.
- **Утилізація ресурсів:** споживання CPU, пам'яті подів, використання обчислювальних ядер GPU та пам'яті VRAM.
- **Стабільність платформи:** кількість активних реплік, кількість перезапусків подів (restart count), фіксація аварійних завершень через нестачу пам'яті (OOMKilled).
- **Фінансові показники:** щоденна вартість інфраструктури через інструменти виділення витрат (Kubecost, AWS Cost Allocation Tags).

### Обов'язкові алерти
1. Зростання частки помилок 5xx понад 1% за 5 хвилин.
2. Перевищення порогу латентності p99 понад узгоджений ліміт SLA.
3. Циклічні перезапуски подів моделі (CrashLoopBackOff або OOMKilled).
4. Зависання масштабування: наявність подів у стані Pending понад 3 хвилини через нестачу нод.
5. Неконтрольоване зростання витрат: споживання бюджету перевищує прогнозований денний ліміт на 20%.

### Чекліст готовності до запуску (Production-Readiness Checklist)
- [ ] Для всіх контейнерів коректно налаштовано проби стану: startupProbe, livenessProbe, readinessProbe.
- [ ] Жорстко задано значення requests і limits по CPU, RAM та GPU для кожного сервісу.
- [ ] Налаштовано горизонтальне автоскейлювання подів (HPA) на базі метрик черги або завантаження.
- [ ] Налаштовано бюджети порушення доступності подів (PodDisruptionBudget) для захисту від раптової втрати реплік при оновленні нод.
- [ ] Реалізовано механізм плавного завершення роботи (graceful shutdown) для коректного доопрацювання активних інференс-запитів.
- [ ] Проведено стрес-тестування та симуляцію відмови окремих зон доступності на staging.
- [ ] Налаштовано централізований експорт логів і метрик, черговий канал сповіщень активовано.

## 7. Таблиця ризиків та рішень

| Ризик | Наслідок | Як зменшити ризик |
|---|---|---|
| **Відсутність resource quotas** | Dev-середовище або помилка у коді експерименту споживає всі ресурси кластера. | Встановити суворі ResourceQuota та LimitRange для кожного namespace. |
| **Постійно увімкнені GPU-ноди** | Значні перевитрати хмарного бюджету на обчислювальні вузли, що простоюють. | Впровадити автоскейлер (Karpenter) з правилом scale-to-zero для GPU-груп вузлів. |
| **Відсутність RBAC і прямі доступи до prod** | Людська помилка або несанкціонована зміна конфігурації призводить до падіння сервісу. | Обмежити доступ за принципом найменших привілеїв, перевести деплой виключно на автоматизований GitOps/CI/CD. |
| **Відсутність моніторингу та алертів** | Деградація сервісу та помилки виявляються тільки після скарг кінцевих користувачів. | Налаштувати Prometheus, Grafana, експортери метрик GPU та алерти по SLA/SLO. |
| **Аварійне завершення подів через OOM (Out Of Memory)** | Модель падає при великому пакеті вхідних даних, викликаючи чергу відмов. | Налаштувати валідацію розміру запитів на рівні API, встановити ліміти пам'яті з запасом, додати моніторинг OOMKilled. |
| **Довгий холодний запуск контейнерів з моделями** | При сплеску трафіку нові поди стартують кілька хвилин через завантаження ваг, що призводить до затримок. | Використовувати кешування образів і ваг на вузлах, налаштувати випереджальне масштабування за розкладом або швидкістю зростання черги. |

## 8. Висновок

Впровадження платформи Amazon EKS для AI/ML-продукту трансформує підхід до життєвого циклу моделі, збалансовуючи інженерну швидкість та операційну надійність:
- **Бюджет:** поділ груп вузлів на CPU та динамічні GPU з масштабуванням до нуля усуває оплату за простій дорогих ресурсів.
- **Швидкість доставки (delivery):** чітке розділення середовищ та автоматизований конвеєр розгортання скорочують час переходу від навченого артефакту до діючого API без ручного втручання.
- **Безпека:** сувора ізоляція промислового контуру на рівні окремого кластера та відсутність прямого людського доступу усувають ризик компрометації даних чи випадкових збоїв.
- **Стабільність:** декларативний контроль стану контейнерів, ліміти ресурсів та автоматичне самовідновлення гарантують безперервну доступність сервісу навіть під час пікових навантажень.
