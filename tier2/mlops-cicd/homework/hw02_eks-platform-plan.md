# Архітектурно-управлінський план EKS-платформи для AI/ML-продукту

Цей документ визначає структуру платформи Amazon EKS для розміщення сервісу машинного навчання з фокусом на баланс надійності згідно з SLA, безпеки та витрат (FinOps).

---

## 1. Середовища

Для забезпечення стабільності та керованості життєвого циклу продукту формуються три ізольовані середовища:
- **dev (розробка):** швидкі експерименти та налагодження коду; допускаються тимчасові збої;
- **staging (тестування):** передрелізна валідація, виявлення помилок, оцінка затримки (latency) і якості моделей; конфігурація повністю дублює prod;
- **prod (промислова експлуатація):** обробка реальних запитів клієнтів із суворим дотриманням SLA/SLO.

**Чому неприпустима робота без ізоляції:**  
Спільний простір без меж створює пряму загрозу відмови бізнес-сервісів: експериментальна модель у dev може спожити всю доступну оперативну пам'ять або квоту GPU на вузлах, спричинивши збій і недоступність промислового API. Крім того, відсутність ізоляції створює критичний ризик витоку конфіденційних клієнтських даних у тестові логи та унеможливлює надійне розмежування прав доступу.

## 2. Namespace strategy або multi-cluster strategy

**Обраний підхід:** комбінована дворівнева стратегія (два окремі EKS-кластери):
1. **Кластер non-prod:** об'єднує середовища dev та staging, ізольовані одне від одного через Kubernetes namespaces, NetworkPolicies та ResourceQuotas.
2. **Кластер prod:** виділений фізичний кластер виключно для промислової експлуатації.

**Обґрунтування вибору:**
- **Безпека:** повна ізоляція на рівні хмарної мережі (VPC) та Control Plane. Помилки тестування або збої в non-prod технічно не можуть зачепити робочий трафік.
- **Вартість:** спільний non-prod кластер економить фіксовану вартість Control Plane ($0.10/год за кластер) та системних компонентів моніторингу й логування, не переплачуючи за окремі кластери для dev і staging.
- **Складність підтримки:** адміністрування двох кластерів (prod та non-prod) зберігає низьку операційну складність для команди, забезпечуючи при цьому базову доступність Control Plane від AWS на рівні SLA 99,95%.
- **Ізоляція production та ризик впливу dev/staging:** ризик впливу навантажень dev/staging на production зведений до нуля завдяки фізичному розділенню кластерів.

## 3. Workloads

У кластері розгортаються такі робочі навантаження:

| Workload | Профіль та режим роботи | Необхідні ресурси (CPU / GPU) |
| :--- | :--- | :--- |
| **Inference API** | Реальний час, низька затримка, HPA-автомасштабування | **CPU** достатньо для оптимізованих та квантованих моделей. **GPU** лише за крайньої потреби (важкі LLM або комп'ютерний зір високої роздільної здатності). |
| **Batch jobs** | Періодичний розрахунок скорингу, генерація ембеддингів | **CPU** для підготовки даних; короткостроковий запуск **GPU** за розкладом або за наявності черги. |
| **Monitoring / Logging** | Prometheus, Grafana, FluentBit (постійне базове навантаження) | Виключно **CPU** (інстанси загального призначення). |
| **Training / Heavy inference** | Оцінка нових моделей, валідація на staging/dev, донавчання | **GPU** (виділені графічні процесори з високою пропускною здатністю VRAM). |

## 4. CPU/GPU node group planning

**Чому CPU- і GPU-навантаження обов'язково розділяти:**  
GPU-сервери у 5-10 разів дорожчі за CPU. Якщо тримати їх в одній спільній групі вузлів, звичайні системні або легкі сервіси займуть дорогі ноди, що призведе до блокування важких завдань і колосальних перевитрат бюджету.

- **Задачі для CPU node group:** легкий інференс квантованих моделей, веб-сервери API, черги повідомлень, сервіси моніторингу та збору логів.
- **Задачі для GPU node group:** важкий інференс (heavy inference), пакети генерації ембеддингів великими трансформерами, експерименти з fine-tuning.
- **Чому GPU-ноди не можна тримати постійно увімкненими:** кожна година простою GPU-ноди генерує відчутні прямі фінансові збитки без жодної бізнес-користі.
- **Ризики для бюджету та їх вирішення:**
  - *Ізоляція:* застосування механізму taints `sku=gpu:NoSchedule` та tolerations, щоб жоден CPU-сервіс випадково не запустився на GPU-ноді.
  - *Масштабування до нуля (Scale-to-Zero):* налаштування автоскейлера Karpenter на вимкнення GPU-нод до 0 за відсутності завдань у черзі.

## 5. Governance: доступи, quotas, ownership

- **Доступи та матриця RBAC:**
  - *dev:* інженери мають права на створення та редагування ресурсів у межах свого namespace;
  - *staging:* доступ розробників обмежено режимом Read-Only, деплой відбувається автоматично через CI/CD;
  - *prod:* прямий доступ людей заборонено. Зміни вносяться виключно через GitOps/CI/CD. За крайньої потреби надається тимчасовий доступ адміністратора за процедурою break-glass.
- **Квоти (ResourceQuotas & LimitRanges):**
  - Обов'язкове встановлення `ResourceQuota` для кожного namespace (сумарні ліміти CPU, RAM та ліміт GPU), що гарантує захист кластера від монополізації ресурсів однією командою.
  - Впровадження `LimitRange` на рівні окремих подів для запобігання запуску контейнерів без зазначених requests та limits.
- **Безпека через IRSA (IAM Roles for Service Accounts):** повна відмова від статичних AWS-ключів усередині контейнерів або Secrets; кожен под отримує тимчасові токени з мінімально необхідними правами до хмарних ресурсів.
- **Тегування (FinOps):** усі ресурси маркуються обов'язковими тегами (`Environment`, `Project`, `Owner`). Це дозволяє через Kubecost точно розраховувати юніт-економіку: вартість одного запиту до моделі (cost-per-prediction).
- **Розподіл зон відповідальності (Ownership):**
  - *MLOps / DevOps / Platform Team:* відповідають за базову інфраструктуру, мережу, оновлення кластера, Karpenter і драйвери GPU;
  - *ML-інженери:* відповідають за саму модель, оптимізацію коду інференсу та пакування контейнера;
  - *AI Product Manager:* відповідає за бізнес-метрики, API, дотримання SLA/SLO, пріоритезацію моніторингу та загальний контроль бюджету платформи.

## 6. Monitoring та production-readiness

**Метрики під постійним контролем:**
- *Продуктові та API-метрики:* затримка інференсу (latency: p95, p99), частка помилок (error rate: HTTP 5xx), доступність сервісу (availability).
- *Інфраструктурні метрики:* утилізація CPU та RAM, навантаження графічних чіпів та використання відеопам'яті (GPU/VRAM usage), кількість активних подів (pod count), кількість перезапусків (restart count), аварійні завершення через нестачу пам'яті (OOMKilled).
- *Фінансові метрики:* вартість інфраструктури та темп витрат у реальному часі.

**Критичні алерти перед production-запуском:**
- Рівень помилок HTTP 5xx > 1% протягом 5 хвилин;
- Перевищення p99 latency понад поріг, встановлений у SLA;
- Зациклений перезапуск подів (CrashLoopBackOff) або фіксація подій OOMKilled;
- Перебування подів у стані Pending > 3 хвилин (дефіцит ресурсів або збій автоскейлера);
- Стрибок денного бюджету інфраструктури понад 20%.

**Чекліст готовності до релізу (Production-Readiness):**
- [ ] Налаштовано проби стану (liveness, readiness, startup) та коректний graceful shutdown;
- [ ] Жорстко задано requests і limits (CPU/RAM/GPU), налаштовано HPA;
- [ ] Впроваджено IRSA, повністю відсутні статичні AWS-ключі;
- [ ] Налаштовано PodDisruptionBudget та перевірено стійкість до відмови AZ на staging;
- [ ] Промарковано теги обліку витрат, активовано експорт логів і доставку сповіщень черговим.

## 7. Ризики та рішення

| Ризик | Наслідок для продукту | Як зменшити ризик (Мітигація) |
| :--- | :--- | :--- |
| **Відсутність resource quotas** | Dev-середовище може спожити забагато ресурсів і спричинити відмову сервісів | Встановити суворі `ResourceQuota` та `LimitRange` для кожного namespace |
| **Постійно увімкнені GPU-ноди** | Зайві витрати та стрімке вичерпання бюджету проєкту | Масштабувати GPU-ноди тільки за потреби через Karpenter (scale-to-zero) |
| **Немає RBAC / надмірні доступи** | Прямий ручний доступ до prod, ризик людської помилки та downtime | Розділити ролі й доступи через RBAC, впровадити деплой тільки через GitOps/CI/CD |
| **Немає monitoring / алертингу** | Проблеми виявляються занадто пізно від невдоволених користувачів | Налаштувати моніторинг ключових метрик (latency, 5xx, OOM) та алерти перед релізом |
| **Збій через пам'ять (OOMKilled)** | Падіння поду під час обробки великого пакета даних, деградація доступності | Валідація розміру вхідних запитів у API, запас у limits, моніторинг споживання RAM |
| **Витік статичних AWS-ключів** | Компрометація даних клієнтів або несанкціоноване використання хмари | Повна відмова від постійних ключів, впровадження тимчасових ролей через IRSA |

---

## Висновок

Платформа на базі Amazon EKS забезпечує для AI-продукту баланс ключових факторів: оптимізацію сукупної вартості володіння (TCO) завдяки динамічному scale-to-zero для дорогих GPU-нод; високу швидкість виведення оновлень на ринок (time-to-market) завдяки стандартизованим середовищам і GitOps; а також захист бізнесу завдяки фізичній ізоляції prod-середовища, базовому SLA EKS 99,95% та безпеці на рівні IRSA.
