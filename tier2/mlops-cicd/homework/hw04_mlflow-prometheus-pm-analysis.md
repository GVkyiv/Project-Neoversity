## 1. Бізнес-контекст ML-задачі

### 1.1. Яку задачу вирішує модель і яке рішення підтримує
Модель вирішує задачу багатокласової класифікації рослинних культур на базі морфологічних характеристик (датасет Iris: 150 спостережень, 3 класи: *setosa*, *versicolor*, *virginica*; 4 числові ознаки: довжина та ширина чашолистка і пелюстки). Розподіл даних: 70% train (105 екземплярів) / 30% test (45 екземплярів), стратифікований (`stratify`, `split_random_state = 7`).

У бізнес-середовищі (агротехнічний контроль, тепличне господарство, сортовий насіннєвий контроль або автоматизоване сортування рослинної продукції) модель підтримує автоматичну селекцію та вибраковку сортів під час приймання або фасування партій. Модель замінює тривалу ручну експертизу сортової належності автоматичним швидким інференсом.

### 1.2. Цільові користувачі результату моделі
- **Оператори лінії контролю якості та агрономи-технологи:** отримують миттєву класифікацію партії та рекомендацію щодо сортової чистоти.
- **Керівники складських та логістичних операцій:** спираються на класифікацію для маршрутизації партій за температурними режимами та ціновими категоріями.
- **Супутні автоматизовані системи (ERP, WMS):** приймають рішення про списання, перепакування або зміну ціни партії без ручного втручання.

### 1.3. Ризики та вартість помилок моделі
У задачі 3 класи: клас *setosa* лінійно відокремлюваний і розпізнається практично безпомилково, тоді як класи *versicolor* та *virginica* мають спільну границю розподілу ознак.
- **Помилка плутанини Versicolor ↔ Virginica:** є найбільш небезпечною для бізнесу. Якщо промисловий чи елітний сорт із високою доданою вартістю помилково класифікується як дешевий аналог (або навпаки, партія з домішками іншого сорту маркується як елітна), бізнес несе прямі фінансові збитки, репутаційні втрати та ризик повернення партій від контрагентів.
- **Самовпевнено хибне рішення:** якщо сервіс з імовірністю 98% видає хибний клас, оператор не поставить партію на повторну ручну верифікацію.

### 1.4. Визначення головної метрики
Для цієї задачі однієї метрики `accuracy` недостатньо:
- **Accuracy** показує загальну частку правильних відповідей. На збалансованому тестовому датасеті (45 зразків, по 15 на кожен клас) accuracy є базовим індикатором успішності.
- **Log Loss (крос-ентропійні втрати):** є критично важливою основною метрикою якості. Вона штрафує модель не лише за помилку, а й за надмірну впевненість у неправильному прогнозі. Для бізнесу модель із вищою каліброваною ймовірністю дає змогу налаштувати поріг невпевненості (prediction confidence threshold): якщо максимальна ймовірність класу < 0.80, партія автоматично надсилається на огляд агроному-експерту.
- **Висновок:** головним критерієм вибору є комбінація: максимальна `accuracy` при обов'язковому мінімумі `loss` (мінімізація штрафу за невпевнені та грубі помилки).

## 3. Визначення кандидата на staging / production

### 3.1. Обраний кандидат
Єдиним легітимним кандидатом є **`rf-depth3` (Run ID: `2ddc4f9d`)**.

### 3.2. Обґрунтування вибору та метрики
1. **Перевага за всіма числовими метриками:**
   - `accuracy` становить **0.956** (лише 2 помилки на 45 тестових спостереженнях проти 3 помилок у `logreg-baseline` та `rf-small`).
   - `loss` знизився до **0.141** (порівняно з 0.191 у бейзлайну, відносне покращення якості прогнозування ймовірностей становить **26.2%**).
2. **Наявність та повнота артефакту моделі (Blocker Factor):**
   - У MLflow зафіксовано повний каталог артефактів:
     - `MLmodel` (декларація сигнатури та лоадера);
     - `model.skops` (серіалізовані ваги ансамблю);
     - `conda.yaml`, `python_env.yaml`, `requirements.txt` (зафіксоване середовище залежностей);
     - `input_example.json`, `serving_input_example.json` (еталонні тестові приклади для healthcheck інференсу).
   - **Жоден інший запуск не містить артефакту моделі.** З точки зору MLOps, навіть якби `logreg-baseline` демонстрував прийнятну якість, його неможливо задеплоїти без повторного навчання, що порушує принцип незмінності релізів (immutability).

### 3.3. Порівняння з baseline та trade-offs
- **Baseline:** `logreg-baseline` (`accuracy` = 0.933, `loss` = 0.191).
- **Приріст якості:** +2.3 процентних пункти accuracy та зниження log loss на 0.050. На тестовій вибірці це означає правильну класифікацію ще однієї граничної рослини.
- **Trade-off складності та ресурсів:**
   - Лінійна модель навчається 362ms і потребує мінімум пам'яті під час інференсу.
   - `rf-depth3` має 100 дерев, навчалася 6.6 секунд. Для реального інференсу 100 дерев на табличних даних із 4 ознаками займають мікросекунди, тому зростання latency для кінцевого користувача є невідчутним.
- **Відтворюваність:** зафіксовано `split_random_state=7`, `random_state=42`, параметри навчання. Проте в полі `Source` стоїть прочерк (`-`), що вказує на запуск з інтерактивного середовища або без прив'язки до Git commit hash. Це зауваження, яке потрібно усунути до релізу.

   - `rf-depth3`: accuracy = 0.9555555555555556, loss = 0.14147528385144287.
   - `logreg-baseline`: accuracy = 0.9333333333333333, loss = 0.19132384578637002.
4. **Діагностика розриву графіка о 08:34 UTC:**
   - На часовому ряді о 08:34 зафіксовано вертикальний розрив ліній на 20-30 секунд.
   - **Причина:** плановий або аварійний перезапуск пода `mlflow-exporter`. Оскільки експортер є stateless-проксі, що читає стан MLflow, після відновлення зв'язку значення метрик відновилися на попередньому рівні без втрати даних чи спотворень.

### 4.2. Управлінський висновок щодо моніторингу
- **Grafana / Prometheus показує:** централізований агрегований зріз метрик експериментів за всіма типами моделей, дозволяючи фільтрувати запуски за лейблами без входу в MLflow UI.
- **MLflow UI показує:** повну історію експерименту, детальні гіперпараметри, тривалість, авторів та, найголовніше, сховище фізичних файлів моделей (Artifact Store).
- **Разом ці інструменти допомагають:** інженерам і Product Manager швидко порівнювати моделі на єдиному дашборді та перевіряти технічну цілісність результатів навчання.
- **Але для production-рішення ще бракує:**
  - **Онлайн-метрик інференсу:** затримки відповіді сервісу (latency p95/p99), кількості запитів (throughput / RPS), частки технічних помилок (HTTP 4xx/5xx).
  - **Метрик споживання ресурсів:** використання CPU, пам'яті (RAM) та ризику аварійного завершення (OOMKilled) у Kubernetes pod.
  - **Метрик моніторингу даних (Data Drift):** відстеження зміни розподілу вхідних ознак відносно навчального датасету в реальному часі.

## 8. Додаток: Практичний досвід застосування MLflow у власній робочій задачі (LLM Benchmarking для протоколювання)

Одразу після вивчення теми 9 я застосував отримані знання на практиці у власному робочому проєкті з відбору моделі для складання протоколів зустрічей.

### 8.1. Мета та методологія
- **Задача:** обрати найбільш економічну відкриту LLM для автоматичного створення структурованих протоколів робочих зустрічей за фіксованим промптом.
- **Інструмент:** реалізовано скрипт тестування (`compare.py`) на базі OpenRouter API, куди надсилаються робочі промпти та реальні робочі стенограми (із дотриманням конфіденційності).
- **Інтеграція MLflow:** для прозорого порівняння моделей підключено MLflow Tracking. Кожен запуск автоматично фіксує модель, вхідні параметри, тривалість, токени, вартість у USD та перевірку валідності структури протоколу.
