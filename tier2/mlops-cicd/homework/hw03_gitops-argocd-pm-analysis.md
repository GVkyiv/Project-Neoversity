# PM-аналіз GitOps-процесу для ML-сервісу

Argo CD • Управлінський погляд Product Manager

> Мета роботи: показати, як зробити випуск змін контрольованим і прозорим, як розподілити відповідальність у команді та як зменшити ризик для користувачів і бізнесу.

---

## 1. Як працює GitOps-процес

GitOps: це спосіб керувати розгортанням сервісу через зміни, зафіксовані в Git. У репозиторії зберігається опис того, як сервіс має бути налаштований. Argo CD порівнює цей опис із фактичним станом середовища та показує, чи відповідають вони одне одному.

**Зміна в Git → Перевірка та погодження → Застосування через Argo CD → Перевірка результату → Рішення про реліз**

### Послідовність дій

1. Інженер готує зміну в репозиторії: наприклад, оновлює версію образу інференсу або налаштування в Helm values (values.yaml).
2. Команда перевіряє зміну. Для production додатково діють погодження, визначені правилами команди.
3. Після погодження Argo CD застосовує зміни до потрібного середовища: автоматично або після ручного запуску, залежно від установленої політики.
4. Команда перевіряє статус у Argo CD та фактичну роботу сервісу: чи проходять тестові запити, чи не зросла кількість помилок і чи прийнятна швидкість відповіді.
5. Product Manager разом із технічною командою вирішує, чи можна вважати реліз успішним, чи потрібні додаткові дії або відкат.

### Що важливо розуміти PM

- **Git як джерело бажаного стану:** Git: це зафіксований опис бажаного стану сервісу (desired target state). Історія змін допомагає з'ясувати, хто, коли й що змінив.
- **Що контролює Argo CD:** Argo CD показує, чи відповідає середовище опису в Git. Він не приймає продуктових рішень і не гарантує, що кожна зміна безпечна.
- **Ризик розбіжності (drift):** Ручна зміна середовища поза Git створює розбіжність. Це називають drift: фактичний стан відрізняється від зафіксованого.
- **Комплексна оцінка успіху:** Успішне застосування зміни ще не означає, що продукт готовий для користувачів. Потрібно перевірити технічний стан і продуктові показники.

**Розподіл відповідальності:** PM відповідає за вплив на користувачів, критерії успіху, пріоритети та координацію рішення. Tech Lead / Platform-команда відповідають за технічну діагностику, безпечний спосіб застосування зміни й реалізацію відкату.

## 2. Ручне розгортання та GitOps: порівняння

| Критерій | Ручне розгортання | GitOps із Argo CD |
| :--- | :--- | :--- |
| **Де зафіксовано зміни** | Можуть бути локальні файли або команди окремого інженера. | Зміни зберігаються в Git і мають історію. |
| **Погодження** | Може залежати від особистої домовленості. | Можна визначити обов'язкову перевірку та погодження до застосування. |
| **Прозорість** | Складніше швидко зрозуміти, що саме змінили. | Видно автора, зміст зміни та історію погодження. |
| **Виявлення розбіжностей** | Розбіжність може залишитися непоміченою. | Argo CD показує, коли середовище не відповідає опису в Git (статус OutOfSync). |
| **Відновлення після невдалого релізу** | Може потребувати пошуку старих файлів і повторення ручних кроків. | Команда може повернути попередню конфігурацію через контрольовану зміну в Git (git revert). |
| **Основний ризик** | Залежність від конкретного виконавця та недостатня відтворюваність. | Помилкова зміна все одно можлива, якщо процес перевірки й погодження слабкий. |

### Висновок для PM

GitOps особливо корисний, коли сервіс регулярно оновлюється, має кілька середовищ і обслуговує реальних користувачів. Він робить зміни зрозумілішими й контрольованішими, але сам по собі не усуває всі ризики. Для невеликого навчального експерименту чи PoC ручний підхід може бути прийнятним; для production варто мати формалізований процес із Git, перевірками, погодженнями та планом відновлення.

## 3. Політики для dev, staging і prod

Різні середовища мають різну ціну помилки. Тому однакові правила для всіх середовищ не завжди доречні.

| Середовище | Автоматичне застосування (auto-sync) | Самовідновлення (self-heal) | Видалення ресурсів (prune) | Погодження та контроль |
| :--- | :--- | :--- | :--- | :--- |
| **dev** | Зазвичай увімкнене для швидкої роботи. | Можна увімкнути. | Можна увімкнути, якщо дані не є критичними. | Спрощене погодження; важливі швидкі експерименти. |
| **staging** | Можна увімкнути після погодження змін. | Можна увімкнути. | Вимкнене або додатково захищене, якщо є ризик втрати потрібних даних. | Перевірка інженером перед релізом; перевірка сценаріїв користувача. |
| **prod** | Вимкнене за замовчуванням; зміна застосовується контрольовано. | Лише за погодженою політикою, з урахуванням плану дій під час інциденту. | Вимкнене або захищене окремими правилами. | Обов'язкове технічне погодження; PM підтверджує готовність із погляду продукту та користувачів. |

### Чому саме так

1. У dev пріоритетом є швидкість навчання та розробки. Тут можна приймати більше контрольованих ризиків.
2. Staging потрібне для перевірки зміни до виходу до користувачів. Воно має допомогти виявити проблеми заздалегідь.
3. У production помилка може вплинути на користувачів, дані, репутацію або дохід. Тому зміни мають проходити перевірку, а права на їх застосування: бути чітко визначеними.
4. Prune може видалити ресурс, який більше не описаний у Git. Перед його використанням у production потрібно впевнитися, що видалення безпечне (особливо для баз даних PostgreSQL чи сховищ артефактів моделей); за відсутності такого підтвердження краще заборонити автоматичне видалення.
5. Self-heal може скасувати ручну зміну, зроблену інженером під час аварії. Команда має заздалегідь домовитися, як діяти в таких випадках, щоб автоматизація не заважала відновленню.

Це запропонована базова політика. Остаточні налаштування визначає технічна команда відповідно до архітектури сервісу, вимог безпеки та критичності даних.

## 4. Реєстр основних ризиків

PM не повинен самостійно налаштовувати кластер, але має бачити ризики, визначати їхній вплив на продукт і перевіряти, що є відповідальний та погоджений спосіб зменшення ризику.

| № / Ризик | Можлива причина | Вплив на продукт | Пріоритет | Управлінська дія та відповідальний |
| :--- | :--- | :--- | :--- | :--- |
| **1. Помилкова зміна потрапила в Git** | Недостатня перевірка або відсутність погодження. | Сервіс може працювати неправильно після релізу. | Високий | Вимагати перевірку змін, визначених погоджувачів і зрозумілий журнал рішень. Реалізація: Tech Lead. |
| **2. Збійний реліз застосувався автоматично в prod** | Надто вільна політика автоматичного застосування. | Помилки для користувачів або недоступність сервісу. | Критичний | Для prod вимкнути автоматичне застосування за замовчуванням; визначити, хто й коли дозволяє реліз. Власник: Platform/Tech Lead. |
| **3. Випадково видалено важливий ресурс** | З Git прибрали опис ресурсу, а система автоматично видалила його в середовищі. | Можлива втрата даних або зупинка сервісу. | Критичний | Заборонити або додатково захистити автоматичне видалення в prod; перевіряти вплив змін і наявність резервного відновлення. Власник: Platform-команда. |
| **4. Середовище відрізняється від Git (drift)** | Зміни внесли вручну поза погодженим процесом. | Наступний реліз може скасувати важливу правку або відтворити проблему. | Високий | Визначити порядок аварійних змін і вимагати фіксувати їх назад у Git. Власник: Tech Lead. |
| **5. Немає перевіреного плану відкату** | Команда не перевірила, як повернути попередню версію. | Збільшується час простою. | Високий | До production перевірити сценарій відкату на staging, призначити відповідального й погодити критерії запуску відкату. |
| **6. Не визначено власника сервісу** | Незрозуміло, хто координує реакцію на збій. | Втрачається час, рішення відкладаються. | Високий | Зафіксувати власника сервісу, технічного відповідального, черговий контакт і порядок ескалації. |
| **7. Не вистачає обчислювальних ресурсів** | Нова версія потребує більше ресурсів, ніж доступно. | Оновлення може затриматися або сервіс не запуститься. | Середній / високий | Попросити платформну команду перевірити доступність ресурсів і провести перевірку на staging до production. PM контролює ризик і готовність, а не налаштовує інфраструктуру. |

*Примітка:* рівні пріоритету попередні. Команда має уточнити їх з огляду на критичність сервісу, обсяг потенційної втрати, кількість користувачів і вимоги до доступності.

## 5. Як PM читає статуси Argo CD

| Статус | Просте пояснення | Що робить PM |
| :--- | :--- | :--- |
| **Synced** | Фактичний стан відповідає опису в Git. | Перевірити, що це очікувана версія та правильне середовище. Сам по собі статус не підтверджує успіх продукту. |
| **OutOfSync** | Середовище відрізняється від опису в Git. | Запитати, чи це очікувана зміна перед синхронізацією, чи незапланована розбіжність. Не запускати Sync без розуміння причини. |
| **Healthy** | Argo CD вважає ресурси застосунку здоровими. | Додатково перевірити тестовий сценарій і продуктові показники. Healthy не гарантує, що всі функції працюють правильно. |
| **Degraded** | Є проблема зі станом застосунку або його ресурсів. | Негайно залучити технічного відповідального, з'ясувати вплив на користувачів і потребу у відкаті. |
| **Progressing** | Зміни ще застосовуються або система переходить до нового стану. | Перевірити, чи вкладається процес у погоджений час. Якщо ні: попросити команду пояснити затримку. |
| **Missing** | Очікуваний ресурс не знайдено в середовищі. | Уточнити в технічної команди причину, вплив і план відновлення. |

### Запитання, які PM має поставити команді

1. Це очікувана зміна чи незапланована розбіжність?
2. У якому середовищі сталася проблема і чи зачепила вона реальних користувачів?
3. Які показники змінилися: частка помилок, час відповіді, доступність або виконання ключового сценарію?
4. Які варіанти дій є, скільки часу займе відновлення та хто ухвалює технічне рішення?
5. Чи потрібен відкат і як ми перевіримо, що сервіс справді відновився?

## 6. План реагування на невдалий реліз

Сценарій: після релізу в production статус змінився на Degraded, зросла кількість помилок або користувачі не можуть виконувати ключовий сценарій.

**Виявити → Оцінити вплив → Узгодити рішення → Відновити → Перевірити → Зробити висновки**

### Порядок дій

1. **Виявлення:** Моніторинг або звернення користувачів сигналізує про проблему. PM фіксує час початку та первинний вплив, а черговий інженер починає технічну перевірку.
2. **Оцінка впливу:** Команда перевіряє статус Argo CD, показники помилок і швидкості відповіді. PM уточнює, які користувачі та функції постраждали.
3. **Рішення:** Tech Lead оцінює технічні варіанти. PM допомагає визначити пріоритет із погляду бізнесу: швидко повернути попередню робочу версію чи виправляти поточну. Якщо безпечне виправлення не є очевидним, відкат слід серйозно розглянути.
4. **Відновлення:** Основний контрольований варіант: скасувати проблемну зміну в Git (git revert) і застосувати попередню конфігурацію через погоджений процес. У критичній ситуації технічна команда може скористатися аварійною процедурою, визначеною заздалегідь; після цього фактичний стан потрібно узгодити з Git.
5. **Перевірка:** Команда перевіряє статуси Argo CD, виконує тестовий запит або ключовий сценарій користувача та підтверджує, що показники повернулися до погоджених меж.
6. **Комунікація:** PM повідомляє зацікавленим сторонам про вплив, поточний стан, очікуваний наступний крок і момент наступного оновлення.
7. **Після інциденту:** Команда аналізує причину без пошуку винних, визначає, чому проблему не виявили раніше, і фіксує конкретні покращення.

### Критерії завершення інциденту

- Сервіс знову виконує ключовий сценарій користувача.
- Argo CD показує очікуваний стан, а команда підтвердила, що розбіжності не залишилися без пояснення.
- Кількість помилок і час відповіді повернулися в межі погоджених SLO/SLA або інших критеріїв сервісу.
- Визначено власника подальших дій і повідомлено зацікавлені сторони.

Часові нормативи (наприклад, скільки хвилин чекати перед відкатом) потрібно визначати на основі критичності сервісу, погоджених вимог до відновлення та фактичної здатності команди реагувати. Не варто задавати універсальний поріг без такого обґрунтування.

## 7. Чекліст готовності до production

Перед запуском команда має підтвердити, що процес релізу контрольований. PM перевіряє наявність домовленостей і доказів готовності; технічні спеціалісти підтверджують конкретні налаштування.

| № | Що перевірити | Очікуваний результат |
| :--- | :--- | :--- |
| **1** | **Відповідальність** | Визначені власник сервісу, технічний відповідальний і контакт на випадок інциденту. |
| **2** | **Git як джерело змін** | Зрозуміло, де зберігаються конфігурації та як відстежити історію змін. |
| **3** | **Перевірка змін** | Для production визначені обов'язкове review та погодження до застосування. |
| **4** | **Розділення середовищ** | Dev, staging і prod мають окремі правила; тестова зміна не потрапляє в production без погодженого процесу. |
| **5** | **Контроль релізу** | Для production автоматичне застосування вимкнене за замовчуванням або є чітко обґрунтована й погоджена політика. |
| **6** | **Захист від видалення** | Ризик випадкового видалення ресурсів оцінений; правила prune узгоджені й перевірені. |
| **7** | **Доступи** | Визначено, хто може змінювати конфігурації, погоджувати зміни та запускати production Sync. |
| **8** | **Безпека доступу** | Доступ до інструментів розгортання захищений відповідно до правил організації; секрети не зберігаються у відкритому вигляді. |
| **9** | **Відкат** | Команда перевірила процедуру повернення попередньої версії на staging і знає, хто ухвалює рішення. |
| **10** | **Перевірка працездатності** | Є перевірки, які допомагають зрозуміти, чи запустився сервіс, і тестовий сценарій після релізу. |
| **11** | **Моніторинг** | Є сповіщення про погіршення стану та домовленість, хто на них реагує. |
| **12** | **Аудит змін** | Можна встановити, що змінилося, хто це погодив і коли реліз був застосований. |

## Висновок

Для Product Manager GitOps і Argo CD: це насамперед спосіб зробити випуск змін прозорим, контрольованим і відтворюваним. PM не повинен самостійно налаштовувати Kubernetes або розбиратися в усіх деталях інфраструктури. Його завдання: розуміти основні статуси, поставити правильні запитання, оцінити вплив на користувачів, забезпечити чіткі ролі та погодження, а також вимагати перевіреного плану відновлення.

Рішення про production-реліз має спиратися не лише на статус Argo CD, а й на перевірку ключових сценаріїв і продуктових показників. Технічна команда відповідає за реалізацію та діагностику, а PM: за узгодження ризику з потребами продукту й своєчасну комунікацію.
