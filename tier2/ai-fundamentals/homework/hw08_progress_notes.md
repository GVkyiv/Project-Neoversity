Крок 4. Створення інструментів (Tools)

На цьому етапі визначаються зовнішні інструменти, які чатбот зможе викликати через агента. У термінах LangChain це Tools – функції, загорнуті у спеціальний формат, який модель розуміє й може викликати самостійно.



В актуальному LangChain (v1) рекомендується створювати інструменти через декоратор @tool. Він автоматично:

будує JSON-схему входу на основі анотацій типів (type hints);
використовує docstring як опис інструмента — саме його читає агент, коли вирішує, чи варто цей інструмент викликати;
повертає об’єкт типу BaseTool, сумісний із create_agent.


У прикладі буде три інструменти:

1. calculator — безпечні математичні обчислення через numexpr (LLM погано рахує самостійно, тож краще делегувати це коду).

2. current_datetime — повертає поточну дату / час / день тижня у зручному форматі.

3. wikipedia_search — пошук стислої довідкової інформації в українській (або іншій) Wikipedia через WikipediaAPIWrapper.



Ключові моменти:

Усі параметри мають анотації типів (expression: str, query: str тощо) — це вимога для коректної генерації схеми інструмента.
Docstring має чітко пояснювати, коли варто використовувати інструмент — модель орієнтується саме на нього, а не на назву функції.
Інструменти повертають рядок — це найпростіший формат, який потім легко підставляється у відповідь чатбота.
# КРОК 4. Оголошення інструментів для агента
# 1) Калькулятор на базі numexpr
@tool
def calculator(expression: str) -> str:
    """
    Обчислює математичний вираз.

    Використовуй цей інструмент для будь-яких арифметичних обчислень:
    додавання, віднімання, множення, ділення, дужки, степені.
    Працює з дійсними числами (float). Приклад виразів:
    "2 + 2 * 3", "sin(0.5) + cos(1.0)", "25 * 18 + 145".
    """
    # Базова валідація, щоб відфільтрувати явно некоректні вирази
    allowed_chars = "0123456789+-*/()., eE^"
    if any(ch not in allowed_chars for ch in expression):
        return (
            "Не вдалося обчислити вираз. "
            "Спробуйте використовувати лише числа, +, -, *, /, дужки та крапку."
        )

    try:
        # numexpr безпечно обчислює вираз як векторизовану формулу, а не як eval
        result = ne.evaluate(expression)
        # ne.evaluate повертає масив або скаляр; приводимо до звичайного числа/рядка
        return f"Результат обчислення {expression} = {result.item() if hasattr(result, 'item') else result}"
    except Exception as e:
        return f"Помилка при обчисленні виразу '{expression}': {str(e)}"

# 2) Інструмент для поточної дати/часу
@tool
def current_datetime(query: str) -> str:
    """
    Повертає поточну дату, час або день тижня.

    Використовуй цей інструмент, коли користувач питає:
    - яка сьогодні дата;
    - котра зараз година;
    - який сьогодні день тижня;
    - поточну дату й час разом.

    Параметр query може містити слова: 'date', 'time', 'datetime', 'today', 'now', 'day'.
    """
    now = datetime.now()
    q = query.lower()

    if "date" in q or "today" in q:
        return f"Поточна дата: {now.strftime('%d.%m.%Y')}"
    if "time" in q or "now" in q:
        return f"Поточний час: {now.strftime('%H:%M:%S')}"
    if "datetime" in q or "current" in q:
        return f"Поточна дата та час: {now.strftime('%d.%m.%Y %H:%M:%S')}"
    if "day" in q:
        days_ua = {
            "Monday": "Понеділок",
            "Tuesday": "Вівторок",
            "Wednesday": "Середа",
            "Thursday": "Четвер",
            "Friday": "Пʼятниця",
            "Saturday": "Субота",
            "Sunday": "Неділя",
        }
        day_en = now.strftime("%A")
        return f"Сьогодні: {days_ua.get(day_en, day_en)}"

    # Якщо запит не розпізнано — повертаємо повну інформацію
    return f"Поточна дата та час: {now.strftime('%d.%m.%Y %H:%M:%S')}"

# 3) Інструмент для пошуку в Wikipedia
#    Налаштовуємо обгортку один раз і перевикористовуємо її всередині tool.
wiki_client = WikipediaAPIWrapper(
    lang="uk",              # українська Wikipedia
    top_k_results=1,        # один найрелевантніший результат
    doc_content_chars_max=800,  # обрізаємо текст до ~800 символів
)

@tool
def wikipedia_search(query: str) -> str:
    """
    Шукає стислу довідкову інформацію в українській Wikipedia.

    Використовуй цей інструмент, коли потрібні факти, дати, короткі біографії,
    опис понять чи подій. Повертає короткий текстовий опис за запитом.
    """
    if not query.strip():
        return "Запит до Wikipedia порожній. Сформулюйте, будь ласка, тему пошуку."

    try:
        summary = wiki_client.run(query)
        if not summary:
            return f"Не знайдено релевантної інформації у Wikipedia за запитом: {query}"
        return summary
    except Exception as e:
        return f"Сталася помилка під час звернення до Wikipedia: {str(e)}"

# Збираємо всі інструменти в список — його передамо у create_agent на наступних кроках
tools = [calculator, current_datetime, wikipedia_search]

print("✅ Інструменти calculator, current_datetime, wikipedia_search створено й додано до списку tools.")



Після цього кроку:

у вас є три повноцінних LangChain-інструменти, сумісних із create_agent;
кожен інструмент має чіткий опис (docstring), який пояснює агенту, коли його варто використовувати;
список tools готовий для використання на наступному кроці, де ми створюватимемо ReAct-агента й надамо йому доступ до цих можливостей.


PM-фокус. На цьому етапі важливо побачити, що інструменти задають межі практичної корисності чатбота. Поки система лише генерує текст, вона може пояснювати, але не виконує дій і не отримує перевірених даних іззовні. Після додавання tools бот переходить до іншого рівня поведінки. Він уже не лише формулює відповідь, а й може виконати обчислення, отримати поточну дату або звернутися до зовнішнього джерела фактів.

Для продуктового мислення це означає, що корисність AI-функції визначається не тільки якістю генерації, а й тим, які дії системі дозволено виконувати, наскільки ці дії контрольовані і які ризики вони створюють для стабільності, безпеки та якості відповіді.

Що це означає для продукту. Додавання tools підвищує практичну цінність чатбота, але одночасно ускладнює систему, додає нові точки відмови і вимагає чітких правил, коли саме інструмент має бути використаний.



Крок 5. Ініціалізація мовної моделі (ChatOpenAI) та базова перевірка

На цьому етапі налаштовується чат-модель, яка фактично генеруватиме відповіді.

Використовуємо інтеграційний клас ChatOpenAI з пакету langchain-openai, який інкапсулює роботу з OpenAI Chat Completions API.

Ключові моменти:

Модель автоматично бере API-ключ із змінної середовища OPENAI_API_KEY (ми налаштували її на КРОЦІ 3).
Через параметри (наприклад, temperature, max_tokens) задається характер відповіді: більш креативна чи більш детермінована.
Для навчальної практики з чатботом зручно використати помірно «спокійну» модель: temperature близько 0.3–0.5, щоб відповіді були стабільні, але не повністю «дерев’яні».


У сучасному LangChain 1.x ChatOpenAI є чат-моделлю, яку можна потім передати в create_agent як model.

# КРОК 5. Ініціалізація чат-моделі OpenAI
# На цьому етапі передбачається, що:
# - змінна середовища OPENAI_API_KEY вже встановлена (КРОК 3),
# - пакети langchain, langchain-openai вже встановлені (КРОК 1)

# Створюємо чат-модель.
# Використовуємо gpt-4o-mini як недорогу й достатньо якісну модель для чатбота.
chat_model = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0.4,   # Помірна креативність, щоб відповіді були осмислені й не надто хаотичні
    max_tokens=512,    # Обмеження довжини відповіді
    timeout=30,        # Таймаут на один виклик моделі (секунди)
)

# Швидка перевірка, що модель працює коректно
test_message = "Привіт! Відповідай одним коротким реченням, що ти готовий працювати як чатбот."
response = chat_model.invoke(test_message)

print("✅ Модель успішно ініціалізовано.")
print("Приклад відповіді моделі:")
print(response.content)



Що відбувається на кроці 5:

1. Створюється екземпляр ChatOpenAI

model="gpt-4o-mini" — вказується конкретна модель OpenAI (легка й швидка).
temperature=0.4 — балансує між повною детермінованістю (0.0) і креативністю (>0.7). Для навчального чатбота з інструментами це комфортне значення.
max_tokens=512 — обмежує довжину відповіді, щоб модель не генерувала занадто довгі тексти.
timeout=30 — додатковий захист від «зависань» при мережевих проблемах.
2. Викликається chat_model.invoke(test_message)

Сучасний LangChain 1.x уніфікує виклики через метод invoke(), який приймає або рядок (для простого випадку), або список/словник повідомлень.
Модель повертає об’єкт типу AIMessage, тому контент дістаємо через response.content.
3. Виводиться короткий приклад відповіді, щоб можна було переконатися, що:

API-ключ налаштовано правильно;
бібліотеки імпортуються й працюють;
модель відповідає без помилок.


PM-фокус. На цьому етапі важливо побачити, що підключення моделі — це не просто момент, коли “AI починає працювати”. Насправді саме тут команда задає базові рамки майбутньої поведінки системи. Обрана модель і параметри її виклику визначають, якими будуть якість відповіді, затримка, вартість і передбачуваність взаємодії.

З продуктового погляду особливе значення мають параметри генерації. Вони не є другорядною технічною деталлю, а виступають одним зі способів контролю системи. Якщо модель занадто варіативна, зростає ризик нестабільної поведінки. Якщо вона занадто жорстко налаштована, відповіді можуть стати сухими або недостатньо гнучкими. Тому навіть такий базовий крок, як ініціалізація ChatOpenAI, уже є частиною продуктової логіки.

Що це означає для продукту. Вибір моделі — це не лише питання реалізації. Він визначає якість, швидкість і собівартість AI-функції, а також межі того, що команда взагалі може обіцяти користувачеві.



Крок 6. Створення ReAct-агента з інструментами

На попередніх кроках були підготовлені всі «цеглинки» для чатбота:

налаштована чат-модель chat_model на базі ChatOpenAI;
оголошені три інструменти через @tool: calculator, current_datetime, wikipedia_search.
На цьому кроці ці елементи об’єднуються в агента.

Агент у LangChain v1 — це зв’язка:

мовна модель, яка генерує кроки міркування;
набір інструментів, які можна викликати для дій (рахувати, дізнатись час, знайти факт);
системний промпт, що описує роль асистента та правила використання інструментів;
історія повідомлень у форматі {"role": ..., "content": ...}, яку агент отримує на вхід.
Функція create_agent(...) будує ReAct-агента: модель сама вирішує, коли їй потрібен інструмент, формує виклик, отримує результат і на основі цього формує фінальну відповідь.



Нижче — повний код КРОКУ 6.

# КРОК 6. Створення ReAct-агента з інструментами
# 1) Системний промпт для агента:
#    описуємо роль, мову та правила використання інструментів.
SYSTEM_PROMPT = """
Ти — дружній та уважний AI-асистент на ім'я NovaChat.

Твої завдання:
- відповідати українською мовою, чітко та по суті;
- пояснювати важливі кроки своїх відповідей простими словами;
- коли потрібно виконати розрахунки — використовуй інструмент calculator, а не рахуйте самостійно;
- для запитів про дату, час або день тижня — використовуй інструмент current_datetime;
- для фактологічних запитів (історія, біографії, загальні відомості) — за потреби використовуй інструмент wikipedia_search.

Якщо інструменти не потрібні (наприклад, просте пояснення поняття),
можеш відповідати без їх виклику.
"""

# 2) Збираємо всі оголошені інструменти в список.
#    Назви МАЮТЬ збігатися з тим, як вони були оголошені в КРОЦІ 4 (@tool).
tools = [
    calculator,
    current_datetime,
    wikipedia_search,
]

# 3) Створюємо ReAct-агента за допомогою нового API LangChain 1.x.
agent = create_agent(
    model=chat_model,     # ChatOpenAI з КРОКУ 5
    tools=tools,          # наші інструменти
    system_prompt=SYSTEM_PROMPT,
)

print("✅ Агент NovaChat створений і готовий до тесту.")

# 4) Одноразовий тест: перевіряємо, що агент уміє викликати calculator.
test_messages = [
    {
        "role": "user",
        "content": "Скільки буде 25 * 18 + 145? Поясни, як рахував."
    }
]

# Виклик агента: передаємо історію повідомлень у полі "messages"
result_state = agent.invoke({"messages": test_messages})

# Отримуємо останнє повідомлення як фінальну відповідь
last_message = result_state["messages"][-1]

print("\\n🤖 NovaChat (тестова відповідь):")
print(last_message.content)



Що відбувається на кроці 6:

1. SYSTEM_PROMPT

Описує «персоналію» та поведінку асистента:
ім’я (NovaChat);
мову відповіді (українська);
коли і для чого використовувати кожен з інструментів:
calculator — для будь-яких арифметичних обчислень;
current_datetime — для поточного часу/дати/дня тижня;
wikipedia_search — для фактологічних запитів.
2. tools = [...]

У список додаються саме ті об’єкти, які були оголошені в КРОЦІ 4 через @tool:

calculator,
current_datetime,
wikipedia_search.
3. agent = create_agent(...)

Створює ReAct-агента, який:

поєднує chat_model + tools + SYSTEM_PROMPT;
уміє приймати історію чату у форматі {"messages": [...]};
самостійно приймає рішення, коли викликати інструмент і який саме.
4. gent.invoke({"messages": test_messages})

запускає повний агентний цикл для заданої історії (тут вона містить одне userповідомлення);
якщо моделі потрібен калькулятор, вона сформує виклик calculator, отримає результат, додасть його в історію й сформує фінальну відповідь;
результатом є result_state, де поле result_state["messages"] — повний список повідомлень (system + user + tool + assistant).
5. last_message = result_state["messages"][-1]

останній елемент списку — це фінальна відповідь агента на запит;
її й виводимо як результат роботи бота в тестовому режимі.


PM-фокус. Цей крок є центральним для всієї теми, тому що саме тут система переходить від набору окремих компонентів до внутрішньої оркестрації поведінки. Раніше в нас були модель і tools як окремі частини. Тепер з них формується агент, який вирішує, як саме рухатися до відповіді: чи достатньо згенерувати текст одразу, чи треба спочатку викликати інструмент, отримати результат і лише після цього сформувати фінальне повідомлення.

Для AI Product Manager це особливо важливо як межа між простою LLM-взаємодією і agentic system. Звичайна модель просто відповідає на запит. Агентна система вже оркеструє дії. А це означає, що об’єктом контролю стає не лише відповідь як така, а й маршрут, яким система до неї прийшла. Тут виникають питання про те, коли агент має право використовувати інструмент, які обмеження для нього задаються, як логувати його кроки і як перевіряти, що ці кроки були виправданими.

Саме на цьому рівні системний промпт (SYSTEM_PROMPT) стає одним із головних механізмів керування поведінкою асистента. Для Product Manager важливо вміти не лише оцінювати якість фінальної відповіді, а й формулювати вимоги до стилю, меж допустимої поведінки, умов використання інструментів і правил взаємодії з користувачем.

Що це означає для продукту. Щойно система переходить до агентної логіки, команда починає працювати не лише з якістю тексту, а й із маршрутизацією дій. Саме тут з’являються нові вимоги до контролю, прозорості, дебагу й оцінювання коректності поведінки системи.

Крок 7. Інтерактивний чат із ботом та збереження контексту діалогу

На цьому кроці будується простий консольний інтерфейс для спілкування з агентом NovaChat.

Основна ідея пам’яті тут така:

У змінній messages зберігається повна історія діалогу у форматі списку повідомлень:
{"role": "user" | "assistant" | "tool", "content": "..."}.
На кожному кроці:
додається нове userповідомлення;
у agent.invoke({"messages": messages}) передається вся історія;
агент повертає оновлений стан, де result_state["messages"] — повна історія з врахуванням інструментів і нової відповіді;
ця історія зберігається назад у messages, щоб наступний виклик бачив повний контекст.


Таким чином, роль «пам’яті» виконує змінна messages у Python: агент на кожному кроці отримує все, що було сказано раніше, і може посилатися на попередні питання/відповіді.

Також додамо:

команду exit / вихід / /exit — щоб завершити сесію;
команду /reset — щоб скинути контекст (почати розмову «з нуля» без попередньої історії).


Передумови: перед запуском цього кроку мають бути вже виконані:
КРОК 1–5 (встановлення пакетів, імпорти, ключ, інструменти, модель);
КРОК 6 (створено agent = create_agent(...)).


# КРОК 7. Інтерактивний чат із агентом NovaChat
# З явним роутингом:
#  - матвирази -> calculator
#  - короткі запити "що таке / хто такий / що означає" -> wikipedia_search

import re  # для простих евристик

# 1) Шаблон для "чистих" математичних виразів
MATH_PATTERN = re.compile(r"^[0-9+\\-*/().,\\s]+$")

# 2) Шаблон для простих фактологічних запитів типу "що таке ...", "хто такий ..."
FACT_PATTERN = re.compile(
    r"^\\s*(що таке|хто такий|хто така|що означає)\\b",
    re.IGNORECASE
)

def run_chat_session():
    """
    Інтерактивна сесія спілкування з агентом NovaChat.

    - Пам'ять діалогу зберігається в messages.
    - 'exit' / 'вихід' / '/exit' / 'quit' — завершити.
    - '/reset' — очистити контекст.
    - Якщо рядок схожий на чистий матвираз — викликається calculator.
    - Якщо рядок схожий на фактологічний запит ("що таке ...") — викликається wikipedia_search.
    - Інші випадки — віддаються ReAct-агенту.
    """
    print("\\n" + "=" * 60)
    print("🤖 NovaChat — інтерактивний AI-асистент")
    print("=" * 60)
    print("Можливості:")
    print("  • Математичні обчислення (через інструмент calculator)")
    print("  • Поточна дата, час та день тижня (інструмент current_datetime)")
    print("  • Короткі довідкові факти з Wikipedia (інструмент wikipedia_search)")
    print("  • Загальна розмова з урахуванням попереднього контексту")
    print("\\nСлужбові команди:")
    print("  • 'exit', 'вихід', '/exit', 'quit' — завершити сесію")
    print("  • '/reset' — скинути контекст розмови (почати з чистого аркуша)")
    print("-" * 60)

    # Повна історія чату
    messages: list[dict] = []

    while True:
        try:
            user_input = input("\\n👤 Ви: ").strip()
            if not user_input:
                continue

            lower_input = user_input.lower()

            # 1) Вихід
            if lower_input in ("exit", "вихід", "/exit", "quit"):
                print("\\n👋 Сесію завершено. Гарного дня!")
                break

            # 2) Скидання контексту
            if lower_input in ("/reset", "reset"):
                messages = []
                print("🔄 Контекст розмови скинуто. Починаємо нову сесію.")
                continue

            # 3) Додаємо повідомлення користувача в історію
            messages.append({"role": "user", "content": user_input})

            # 4) Якщо це "голий" матвираз — ідемо напряму в calculator
            if MATH_PATTERN.fullmatch(user_input):
                print("\\n🧮 NovaChat (через calculator):")
                tool_result = calculator.invoke({"expression": user_input})
                print(tool_result)

                # Фіксуємо відповідь як assistant у контексті
                messages.append({"role": "assistant", "content": tool_result})
                continue

            # 5) Якщо це короткий фактологічний запит — напряму в wikipedia_search
            #    (щоб гарантовано показати використання інструмента)
            if FACT_PATTERN.match(user_input):
                print("\\n📚 NovaChat (через wikipedia_search):")
                wiki_result = wikipedia_search.invoke({"query": user_input})
                print(wiki_result)

                # Так само додаємо в історію як відповідь асистента
                messages.append({"role": "assistant", "content": wiki_result})
                continue

            # 6) Усі інші випадки — через агента (ReAct + інструменти за його рішенням)
            print("\\n🤔 NovaChat думає...")
            result_state = agent.invoke({"messages": messages})

            # Оновлюємо історію з того, що повернув агент
            messages = result_state["messages"]
            last_message = messages[-1]

            print("\\n🤖 NovaChat:")
            if isinstance(last_message, dict):
                print(last_message.get("content", ""))
            else:
                print(last_message.content)

        except KeyboardInterrupt:
            print("\\n\\n👋 Сесію перервано користувачем (Ctrl+C). До побачення!")
            break
        except Exception as e:
            print(f"\\n❌ Виникла помилка під час обробки запиту: {e}")
            print("Спробуйте переформулювати запит або повторити пізніше.")

# Запуск інтерактивної сесії
run_chat_session()



Що тут важливо:

1. Пам’ять як список messages

кожне нове повідомлення користувача додається до messages;
агент отримує всю історію {"messages": messages} й повертає її розширену;
ми просто присвоюємо: messages = result_state["messages"], тим самим підтримуючи повний контекст.
2. Команда /reset

очищує messages;
для моделі це виглядає як абсолютно нова сесія, але з тим самим системним промптом (SYSTEM_PROMPT із КРОКУ 6).
3. Формат останнього повідомлення

залежно від версії LangChain, елементи в messages можуть бути або словниками ({"role": ..., "content": ...}), або об’єктами повідомлень (AIMessage, HumanMessage).
Тому вивід зроблений обережно:
last_message["content"] if isinstance(last_message, dict) else last_message.content.
4. Цей підхід уже дає “пам’ять”

хоча ми не використовуємо окремий клас Memory із LangChain, з погляду моделі це повноцінний контекст:
на кожному кроці вона бачить всі попередні репліки діалогу.


Після виконання КРОКУ 7 у тебе є повноцінний консольний чатбот NovaChat, який:

розуміє попередні повідомлення;
вміє викликати калькулятор, час та Wikipedia як інструменти;
підтримує інтерфейс із простими службовими командами (exit, /reset).


PM-фокус. На технічному рівні цей крок показує, як зберігається історія повідомлень і як вона знову передається агенту під час кожного нового виклику. Але в продуктовій площині тут відбувається значно важливіша річ: система починає виглядати для користувача як зв’язна взаємодія. Саме завдяки контексту чат перестає бути серією незалежних звернень і починає сприйматися як безперервний діалог.

Для AI Product Manager це хороший момент, щоб побачити пам’ять не як абстрактну “зручну фічу”, а як конкретне рішення про контекст. Те, що система зберігає і передає далі, впливає і на UX, і на вартість, і на стабільність. Що довшим стає контекст, то дорожчими і повільнішими стають виклики. Отже, рішення про пам’ять — це одночасно UX-рішення, архітектурне рішення і рішення про масштабування.

Окремо варто звернути увагу на /reset. З технічного боку це скидання історії. З продуктового боку це приклад явного контролю над контекстом. У реальних AI-продуктах такі механізми важливі, тому що користувачеві потрібно розуміти, коли система продовжує попередню розмову, а коли починає нову.

Крім якості діалогу, пам’ять безпосередньо впливає на економіку системи. Що довшою стає історія, то більше токенів передається моделі, а отже зростають і вартість, і затримка кожного нового виклику. Для Product Manager це означає, що стратегія memory має оцінюватися не лише з точки зору UX, а й з точки зору unit-економіки, масштабованості та меж прийнятної собівартості взаємодії.

Що це означає для продукту. Контекст визначає, чи взаємодія виглядає цілісною. Але кожне рішення про збереження історії впливає на латентність, витрати та спосіб, у який система поводиться в довгих сесіях.



Крок 8. Автоматичне тестування типових сценаріїв

На цьому кроці виконуються кілька типових запитів до чатбота, щоб подивитись:

коли саме спрацьовує калькулятор;
коли використовується Wikipedia;
як поводиться ReAct-агент у звичайних діалогових запитах;
чи правильно зберігається контекст розмови.
# КРОК 8. Автоматичне тестування типових сценаріїв
def run_automatic_tests():
    """
    Проганяє набір тестових запитів через ту ж саму логіку,
    що використовується в інтерактивному чаті.

    Дає змогу побачити:
    - коли використовується calculator;
    - коли використовується wikipedia_search;
    - як поводиться ReAct-агент у звичайних діалогах.
    """

    test_queries = [
        "Привіт! Як тебе звати?",
        "100/52",
        "23/3",
        "що таке багульник",
        "що означає штучний інтелект",
        "Котра зараз година?",
        "Який сьогодні день тижня?",
        "Запам’ятай, що мене звати Олексій.",
        "Як мене звати?",
    ]

    # Окрема історія повідомлень для тестів
    messages: list[dict] = []

    print("\\n" + "=" * 60)
    print("🧪 АВТОМАТИЧНЕ ТЕСТУВАННЯ CHATBOT NovaChat")
    print("=" * 60)

    for i, query in enumerate(test_queries, start=1):
        print(f"\\nТест #{i}")
        print("-" * 60)
        print(f"👤 Запит користувача: {query}")

        # Додаємо запит у історію
        messages.append({"role": "user", "content": query})

        try:
            # 1) Математичний вираз — використовуємо calculator
            if MATH_PATTERN.fullmatch(query):
                print("🔧 Шлях обробки: інструмент calculator (прямий виклик)")

                tool_result = calculator.invoke({"expression": query})
                answer = tool_result

                print("✅ Відповідь:")
                print(answer)

                # Фіксуємо відповідь як assistant у контексті
                messages.append({"role": "assistant", "content": answer})

            # 2) Фактологічний запит («що таке...», «хто такий...») — wikipedia_search
            elif FACT_PATTERN.match(query):
                print("🔧 Шлях обробки: інструмент wikipedia_search (прямий виклик)")

                wiki_result = wikipedia_search.invoke({"query": query})
                answer = wiki_result

                print("✅ Відповідь (витяг з Wikipedia):")
                print(answer)

                messages.append({"role": "assistant", "content": answer})

            # 3) Всі інші випадки — віддаємо ReAct-агенту
            else:
                print("🔧 Шлях обробки: ReAct-агент (agent.invoke)")

                result_state = agent.invoke({"messages": messages})

                # Оновлюємо історію з того, що повернув агент
                messages = result_state["messages"]
                last_message = messages[-1]

                # Підтримуємо обидва варіанти (dict або AIMessage)
                if isinstance(last_message, dict):
                    answer = last_message.get("content", "")
                else:
                    answer = last_message.content

                print("✅ Відповідь агента:")
                print(answer)

        except Exception as e:
            print(f"❌ Помилка під час обробки тесту #{i}: {e}")

        print("-" * 60)

    print("\\n✅ Автоматичне тестування завершено.\\n")

# Запуск автоматичних тестових сценаріїв
run_automatic_tests()

PM-фокус. Цей етап важливий не лише як фінальна технічна перевірка, а й як перше наближення до продуктового тестування AI-системи. Коли ми проганяємо набір типових сценаріїв, ми фактично дивимося не лише на те, чи працює код, а й на те, як система поводиться в різних класах запитів: коли використовує калькулятор, коли звертається до Wikipedia, як реагує на просту розмову і чи зберігає контекст між повідомленнями.

Для AI Product Manager це дуже важлива зміна оптики. У традиційній програмі тест часто означає перевірку правильного результату. У випадку AI-системи тестування ширше: потрібно дивитися і на коректність, і на послідовність поведінки, і на те, чи виправдано була використана агентна логіка, і на те, як система поводиться на межових або неоднозначних запитах. Тобто тестується не лише код, а й сама поведінка AI-функції.

Що це означає для продукту. Навіть базовий набір тестових сценаріїв допомагає побачити, що AI-систему треба перевіряти не тільки на працездатність, а й на якість рішень, стабільність поведінки та коректність використання інструментів.



Що важливо побачити після проходження ходу роботи

Якщо дивитися на цей розділ лише технічно, то студент послідовно виконує знайомі кроки: налаштовує середовище, підключає модель, створює tools, збирає агента, зберігає історію чату й тестує систему. Але для AI Product Manager тут важливо побачити дещо більше. Усі ці кроки разом показують мінімальний внутрішній контур AI-функції.

Модель тут відповідає за генерацію. Контекст визначає послідовність взаємодії. Інструменти розширюють можливості системи. Агентна логіка керує маршрутом дії. Тестові сценарії дають перше уявлення про поведінку системи в різних ситуаціях. Саме тому цю практичну роботу варто сприймати не як вправу на створення “ще одного чатбота”, а як розбір того, як формується внутрішня логіка AI-системи, яку потім можна перетворити на повноцінну продуктову функцію.
