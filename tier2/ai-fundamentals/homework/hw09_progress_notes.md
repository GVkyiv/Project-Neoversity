Пояснення ключових імпортів:

ChatGoogleGenerativeAI — клас для роботи з моделями Google Gemini через LangChain. Підтримує tool calling, streaming та інші можливості сучасних чат-моделей.

StateGraph — основний клас для побудови графа. Ми створюємо його екземпляр, додаємо вузли та ребра, а потім компілюємо в виконуваний об'єкт.

START та END — константи, що представляють спеціальні псевдо-вузли. Ребро від START визначає точку входу в граф. Ребро до END позначає завершення виконання.

Крок 4. Визначення схеми стану

Схема стану — це «контракт» між вузлами графа. Вона визначає, які дані доступні всім вузлам і як ці дані оновлюються. Для ReAct-агента центральним елементом стану є історія повідомлень.

class AgentState(TypedDict):
    """
    Схема стану для ReAct-агента.
    
    Attributes:
        messages: Історія діалогу, що включає:
            - HumanMessage: повідомлення користувача
            - AIMessage: відповіді моделі (можуть містити tool_calls)
            - ToolMessage: результати виконання інструментів
            
    Редуктор add_messages забезпечує, що нові повідомлення
    ДОДАЮТЬСЯ до списку, а не перезаписують його. Це критично
    важливо для збереження контексту діалогу.
    """
    messages: Annotated[list, add_messages]

print("✅ Схему стану AgentState визначено.")



Чому це важливо:

Анотація Annotated[list, add_messages] — це не просто підказка для IDE. LangGraph використовує її для визначення поведінки при оновленні поля. Без цього редуктора кожен вузол, що повертає {"messages": [...]}, повністю замінював би попередню історію новим списком. З редуктором add_messages нові повідомлення додаються до існуючих, зберігаючи весь контекст діалогу.



Альтернатива — MessagesState:

LangGraph надає готовий клас MessagesState, який вже містить поле messages з редуктором add_messages. Якщо вам потрібен тільки цей один компонент стану, можна використовувати його напряму:

from langgraph.graph import MessagesState

*# Використання готового класу замість власного*
builder = StateGraph(MessagesState)



Тут ми створюємо власний AgentState, щоб краще зрозуміти механіку, і щоб у майбутньому можна було легко додати інші поля (наприклад, лічильник спроб, службові прапорці тощо).



💡Що це означає для кейсу. Схема стану — це продуктове рішення про те, що система "пам'ятає" між кроками. Зараз у стані є лише messages. Але уяви що завтра продуктова вимога змінюється: треба зберігати дієтичні обмеження користувача (ChefBot), його вагу і зріст між сесіями (FitCoach), або список вже вивчених формул (StudyMate). Де саме в коді це змінюється?

Відповідь: тільки в схемі стану — додається нове поле з відповідним редуктором. Решта системи не змінюється. Це і є перевага явного контракту стану: команда точно знає де зберігаються дані і що відбувається при їх оновленні.

Компроміс: чим більше полів у стані, тим більше даних передається між вузлами і зберігається в checkpointer. Для production-системи з тисячами сесій це пряма вартість зберігання і латентність.


Крок 5. Створення інструментів

Інструменти розширюють можливості агента за межі генерації тексту. Створимо три інструменти, кожен з яких демонструє різний тип функціональності: обчислення, робота з датою/часом і пошук у локальній базі знань.





# ============================================================
# ІНСТРУМЕНТ 1: Калькулятор
# ============================================================
@tool
def calculator(expression: str) -> str:
    """Обчислює математичний вираз.
    НЕ рахуй самостійно — завжди використовуй цей інструмент.
    Приклади: "2 + 2 * 3", "100 / 4 + 50", "2 ** 10"
    Args:
        expression: Математичний вираз
    Returns:
        Результат або повідомлення про помилку
    """
    allowed = set("0123456789+-*/()., eE**")
    if not all(ch in allowed for ch in expression.replace(" ", "")):
        return "Помилка: недопустимі символи."
    try:
        result = ne.evaluate(expression)
        value = result.item() if hasattr(result, 'item') else result
        return f"Результат: {expression} = {value}"
    except Exception as e:
        return f"Помилка: {e}"


# ============================================================
# ІНСТРУМЕНТ 2: Поточна дата та час
# ============================================================
@tool
def current_datetime(query: str) -> str:
    """Повертає поточну дату, час або день тижня.
    Args:
        query: "date"/"time"/"day"/"datetime"
    Returns:
        Дата/час українською
    """
    now = datetime.now()
    q = query.lower()
    days_ua = {"Monday":"понеділок","Tuesday":"вівторок","Wednesday":"середа",
               "Thursday":"четвер","Friday":"п'ятниця","Saturday":"субота","Sunday":"неділя"}
    if "day" in q:
        return f"Сьогодні {days_ua.get(now.strftime('%A'), now.strftime('%A'))}"
    elif "time" in q or "now" in q:
        return f"Час: {now.strftime('%H:%M:%S')}"
    elif "date" in q or "today" in q:
        return f"Дата: {now.strftime('%d.%m.%Y')}"
    return f"Зараз {days_ua.get(now.strftime('%A'),'')}, {now.strftime('%d.%m.%Y %H:%M:%S')}"

Важливі моменти щодо інструментів:

1. Docstring визначає поведінку моделі. Модель читає опис інструменту і на його основі вирішує, коли його використовувати. Чим чіткіший опис, тим точніше модель буде обирати інструмент.

2. Type hints обов'язкові. LangGraph використовує анотації типів для побудови JSON-схеми параметрів. Без них інструмент не працюватиме коректно.

3. Інструмент повертає рядок. Результат виконання інструменту повертається моделі як текст. Вона аналізує цей текст і використовує його для формування відповіді користувачу.

4. Безпека калькулятора. Ми використовуємо numexpr замість eval() для обчислень. eval() може виконати довільний Python-код, що є серйозною вразливістю. numexpr обчислює тільки математичні вирази.

5. Локальна база замість зовнішнього API. Інструмент knowledge_base працює з локальним словником замість зовнішнього API (наприклад, Wikipedia). Це забезпечує стабільну роботу без залежності від зовнішніх сервісів. Принцип роботи інструменту при цьому залишається тим самим: агент вирішує коли його викликати, формує запит, отримує результат і використовує його у відповіді.



💡Що це означає для кейсу. Саме тут система переходить від «відповідати текстом» до «виконувати дії». Для продукту це принципова зміна: з'являються нові класи помилок (інструмент повернув неправильний результат, інструмент впав із винятком, інструмент повернув порожній результат), і команда тепер відповідає не лише за якість тексту, а й за коректність дій.

Зверни увагу на docstring калькулятора: «НЕ рахуй самостійно — завжди використовуй цей інструмент». Це не технічна інструкція — це продуктове рішення про те, де проходить межа між тим що робить модель і що робить код. Якщо цей рядок прибрати, модель іноді рахуватиме сама і помилятиметься. Docstring — це частина системного промпту, записана в інструмент.

Крок 6. Ініціалізація мовної моделі

Створюємо екземпляр чат-моделі Google Gemini та прив'язуємо до неї інструменти. Після прив'язки модель «знає» про доступні інструменти і може генерувати структуровані запити на їх виклик.

Параметри моделі:

model="gemini-2.5-flash" — Gemini 2.5 Flash, оптимізована для швидкості та агентних задач. Підтримує tool calling та має великий контекст.

max_output_tokens=1024 — обмежує довжину відповіді. Для агентних задач зазвичай достатньо 512–2048 токенів.


Що робить bind_tools():

Метод .bind_tools(tools) налаштовує модель так, що при кожному виклику вона отримує інформацію про доступні інструменти у форматі JSON-схеми. Модель може включити у свою відповідь структуровані tool_calls — запити на виклик конкретних інструментів з конкретними аргументами.



Крок 7. Створення вузлів графа

Тепер створюємо вузли — обчислювальні одиниці графа. Для ReAct-агента потрібні два вузли: один викликає модель, інший виконує інструменти.

# ============================================================
# ВУЗОЛ 1: Агент (виклик мовної моделі)
# ============================================================
def agent_node(state: AgentState) -> dict:
    """
    Вузол агента: викликає мовну модель з поточною історією діалогу.
    
    Модель аналізує контекст і вирішує одне з двох:
    1. Викликати інструмент — генерує AIMessage з tool_calls
    2. Відповісти напряму — генерує AIMessage зі звичайним текстом
    
    Args:
        state: Поточний стан графа з історією повідомлень
        
    Returns:
        Часткове оновлення стану: словник з новим повідомленням моделі.
        Завдяки редуктору add_messages це повідомлення буде ДОДАНО
        до існуючої історії, а не замінить її.
    """
    # Отримуємо історію повідомлень зі стану
    messages = state["messages"]
    
    # Викликаємо модель з прив'язаними інструментами
    response = llm_with_tools.invoke(messages)
    
    # Повертаємо оновлення стану
    # Редуктор add_messages додасть response до списку messages
    return {"messages": [response]}

# ============================================================
# ВУЗОЛ 2: Інструменти (виконання tool calls)
# ============================================================

# Використовуємо готовий ToolNode з langgraph.prebuilt
# Він автоматично:
# 1. Витягує tool_calls з останнього AIMessage
# 2. Викликає відповідні Python-функції
# 3. Формує ToolMessage з результатами
# 4. Повертає оновлення стану з цими повідомленнями

tool_node = ToolNode(tools)

print("✅ Вузли графа створено:")
print("   • agent_node — викликає Gemini для міркування та прийняття рішень")
print("   • tool_node — виконує інструменти та повертає результати")



Як працює agent_node:

Вузол отримує весь поточний стан, але використовує тільки поле messages. Він передає історію повідомлень у модель, яка генерує відповідь. Ця відповідь може бути:

Звичайним текстом (якщо модель готова відповісти)
AIMessage з tool_calls (якщо модель хоче викликати інструмент)


Вузол повертає {"messages": [response]} — часткове оновлення стану. LangGraph візьме це оновлення і застосує редуктор add_messages, який додасть нове повідомлення до існуючого списку.



Як працює ToolNode:

ToolNode — це готовий клас із langgraph.prebuilt. При створенні він отримує список інструментів. При виклику він:

Бере останнє повідомлення зі стану
Перевіряє, чи є в ньому tool_calls
Для кожного tool call знаходить відповідну функцію та викликає її
Формує ToolMessage з результатом для кожного виклику
Повертає оновлення стану з цими повідомленнями


Це значно спрощує код — нам не потрібно вручну парсити tool calls та викликати функції.



Крок 8. Побудова графа станів

Тепер збираємо всі компоненти в єдиний граф. Визначаємо топологію: які вузли існують, як вони з'єднані, де починається і завершується виконання.

# Створюємо builder графа, параметризований нашою схемою стану
builder = StateGraph(AgentState)

# ============================================================
# ДОДАЄМО ВУЗЛИ
# ============================================================
# Кожен вузол реєструється під унікальним ім'ям
builder.add_node("agent", agent_node)
builder.add_node("tools", tool_node)

# ============================================================
# ДОДАЄМО РЕБРА
# ============================================================
# 1) Точка входу: завжди починаємо з вузла agent
#    START — це спеціальний псевдо-вузол, що позначає вхід у граф
builder.add_edge(START, "agent")

# 2) Умовне ребро від agent:
#    Після виконання agent потрібно вирішити, що робити далі.
#    Функція tools_condition перевіряє останнє повідомлення:
#    - Якщо є tool_calls → повертає "tools"
#    - Якщо tool_calls немає → повертає END
builder.add_conditional_edges(
    "agent",                    # Вихідний вузол
    tools_condition,            # Функція маршрутизації
    {
        "tools": "tools",       # Якщо є tool_calls → йдемо в tools
        END: END                # Якщо немає → завершуємо
    }
)

# 3) Після виконання інструментів повертаємося до agent
#    Це створює цикл: agent → tools → agent → tools → ...
#    Цикл продовжується, поки модель не вирішить відповісти без інструментів
builder.add_edge("tools", "agent")

print("✅ Граф станів побудовано.")
print()
print("📊 Топологія графа:")
print("   START → agent")
print("           ↓")
print("       [tools_condition]")
print("        ↙         ↘")
print("     tools        END")
print("       ↓")
print("     agent (цикл)")



Пояснення топології:

Граф реалізує патерн ReAct:

START → agent: Виконання завжди починається з вузла agent. Модель отримує вхідне повідомлення користувача.
agent → [tools_condition]: Після agent викликається функція маршрутизації tools_condition. Вона перевіряє, чи модель хоче викликати інструмент.
Якщо є tool_calls → tools: Переходимо до вузла tools, який виконує інструменти та повертає результати.
tools → agent: Після виконання інструментів повертаємося до agent. Модель отримує результати і може або викликати ще інструменти, або сформувати фінальну відповідь.
Якщо немає tool_calls → END: Якщо модель вирішила відповісти без інструментів, переходимо до END і завершуємо виконання.


Цикл agent ↔ tools може повторюватися кілька разів, поки модель не отримає достатньо інформації для відповіді.



💡Що це означає для кейсу. Граф робить поведінку системи явною. У темі 8 агент LangChain теж "думав і використовував інструменти" — але ця логіка була прихована всередині create_agent. Тут команда бачить кожен перехід: звідки починається виконання, коли модель передає управління інструментам, коли повертає собі, коли завершує.

Це важливо не лише для розуміння — це важливо для дебагу. Коли система поводиться неочікувано, команда може подивитися на граф і запитати: на якому переході щось пішло не так? Це набагато краще ніж "модель відповіла щось дивне і ми не знаємо чому".

Компроміс: явна топологія графа означає що будь-яка зміна логіки вимагає зміни структури графа. Якщо завтра з'являється новий сценарій — наприклад, валідація відповіді перед поверненням користувачу — це новий вузол і нові ребра, а не просто новий рядок у промпті.


Крок 9. Компіляція графа з checkpointing

Граф потрібно скомпілювати, щоб отримати виконуваний об'єкт. Також підключаємо checkpointer для збереження стану між викликами.

# ============================================================
# СТВОРЮЄМО CHECKPOINTER
# ============================================================
# InMemorySaver зберігає стан у пам'яті процесу.
# Це найпростіший варіант, підходить для:
# - Локальної розробки та тестування
# - Jupyter-ноутбуків
# - Демонстрацій
# Для production рекомендується SqliteSaver або PostgresSaver,
# які зберігають стан у базі даних.

checkpointer = InMemorySaver()

# ============================================================
# КОМПІЛЮЄМО ГРАФ
# ============================================================
# Компіляція перетворює builder на виконуваний об'єкт,
# який підтримує методи invoke, stream, batch тощо.

graph = builder.compile(checkpointer=checkpointer)

print("✅ Граф скомпільовано з підтримкою checkpointing.")
print("   Checkpointer: InMemorySaver (in-memory)")
print()

# Спробуємо вивести структуру графа
try:
    print("📊 ASCII-представлення графа:")
    print(graph.get_graph().draw_ascii())
except Exception:
    # Якщо ASCII-вивід не підтримується, показуємо текстовий опис
    print("📊 Структура графа: START → agent ⇄ tools → END")



Що таке компіляція:

До компіляції builder — це просто об'єкт, що накопичує опис графа: які вузли, які ребра, яка схема стану. Після компіляції ми отримуємо graph — виконуваний об'єкт класу CompiledStateGraph, який реалізує інтерфейс Runnable.



Навіщо потрібен checkpointer:

Без checkpointer граф «забуває» все після кожного виклику. З checkpointer:

Після кожного кроку зберігається знімок стану
При наступному виклику з тим самим thread_id завантажується попередній стан
Історія діалогу зберігається між викликами
Можна реалізувати human-in-the-loop (зупинити граф, дочекатися рішення користувача, продовжити)


Thread ID:

Для роботи з checkpointer потрібно передавати thread_id у конфігурації:

config = {"configurable": {"thread_id": "my-session-123"}}
result = graph.invoke(input, config)



Різні thread_id — це різні незалежні сесії. Кожна має власну історію та контекст.

💡Що це означає для кейсу. InMemorySaver зберігає стан у пам'яті процесу. Це означає: якщо процес Python перезапустився — вся історія всіх сесій втрачена. Для навчального прототипу це нормально. Для реального продукту це означає що користувач втрачає контекст при кожному деплої або перезапуску сервера.

thread_id — це ізоляція сесій. Кожен thread_id — це окрема "розмова" зі своєю історією. Якщо два користувачі використовують одного бота, вони повинні мати різні thread_id інакше вони "бачитимуть" чужі повідомлення.

Крок 12. Дослідження внутрішньої роботи графа

Для кращого розуміння механіки агента дослідимо покрокове виконання графа. Метод stream() дозволяє отримувати проміжні результати після кожного кроку.

# КРОК 12. Трейс виконання
def trace_agent(query):
    print(f"\n{'='*60}\n🔍 ТРЕЙС: {query}\n{'='*60}")
    config = {"configurable": {"thread_id": f"trace-{hash(query) % 10000}"}}
    step = 0
    for event in graph.stream({"messages": [HumanMessage(content=query)]}, config, stream_mode="values"):
        step += 1
        last = event["messages"][-1]
        if isinstance(last, HumanMessage):
            print(f"  {step}. 📥 User: {last.content[:50]}")
        elif isinstance(last, AIMessage) and last.tool_calls:
            for tc in last.tool_calls:
                print(f"  {step}. 🔧 Tool call: {tc['name']}({tc['args']})")
        elif isinstance(last, ToolMessage):
            print(f"  {step}. 📤 Tool result: {last.content[:60]}")
        elif isinstance(last, AIMessage):
            print(f"  {step}. 💬 AI: {last.content[:60]}")
    print(f"  Завершено за {step} кроків.")


trace_agent("Порахуй 123 * 456")
trace_agent("Що таке штучний інтелект?")



Що показує трейс:

Для запиту з математикою ми побачимо приблизно такі кроки:

1. Вхідне повідомлення користувача

2. AIMessage з tool_call для calculator

3. ToolMessage з результатом обчислення

4. AIMessage з фінальною відповіддю



Для звичайного запиту:

1. Вхідне повідомлення користувача

2. AIMessage з відповіддю (без tool_calls)

Це наочно демонструє ReAct-цикл та логіку прийняття рішень агента.



Крок 13. Інтерактивний режим

Створюємо консольний інтерфейс для тривалої взаємодії з агентом. Це дозволяє вести повноцінний діалог із збереженням контексту.

def run_interactive_session():
    """
    Запускає інтерактивну сесію спілкування з агентом.
    
    Підтримувані команди:
    - exit, вихід, quit — завершити сесію
    - /reset — скинути контекст (почати нову сесію)
    - /history — показати історію поточної сесії
    """
    import uuid
    
    print("\\n" + "=" * 60)
    print("🤖 LangGraph AI-Agent (Gemini) — Інтерактивний режим")
    print("=" * 60)
    print()
    print("Можливості агента:")
    print("  • Математичні обчислення (інструмент calculator)")
    print("  • Поточна дата/час (інструмент current_datetime)")
    print("  • Пошук у Wikipedia (інструмент wikipedia_search)")
    print("  • Звичайний діалог із збереженням контексту")
    print()
    print("Команди:")
    print("  • exit / вихід / quit — завершити сесію")
    print("  • /reset — почати нову сесію (скинути контекст)")
    print("  • /history — показати історію діалогу")
    print()
    print("-" * 60)
    
    # Генеруємо унікальний thread_id для цієї сесії*
    thread_id = f"session-{uuid.uuid4().hex[:8]}"
    config = {"configurable": {"thread_id": thread_id}}
    
    print(f"📌 ID сесії: {thread_id}")
    print("-" * 60)
    
    while True:
        try:
            *# Отримуємо введення користувача*
            user_input = input("\\n👤 Ви: ").strip()
            
            if not user_input:
                continue
            
            # ============================================================
            # Обробка команд
            # ============================================================
            lower_input = user_input.lower()
            
            # Команда виходу
            if lower_input in ("exit", "вихід", "quit", "/exit"):
                print("\\n👋 Дякую за спілкування! До побачення!")
                break
            
            # Команда скидання контексту
            if lower_input == "/reset":
                thread_id = f"session-{uuid.uuid4().hex[:8]}"
                config = {"configurable": {"thread_id": thread_id}}
                print("🔄 Контекст скинуто. Розпочато нову сесію.")
                print(f"📌 Новий ID сесії: {thread_id}")
                continue
            
            # Команда показу історії
            if lower_input == "/history":
                try:
                    state = graph.get_state(config)
                    if state.values and "messages" in state.values:
                        print("\\n📜 Історія поточної сесії:")
                        print("-" * 40)
                        for i, msg in enumerate(state.values["messages"], 1):
                            if isinstance(msg, HumanMessage):
                                role = "👤 User"
                            elif isinstance(msg, AIMessage):
                                role = "🤖 AI"
                            elif isinstance(msg, ToolMessage):
                                role = "🔧 Tool"
                            else:
                                role = "❓"
                            content = msg.content[:50]
                            if len(msg.content) > 50:
                                content += "..."
                            print(f"   {i}. [{role}] {content}")
                    else:
                        print("📜 Історія порожня.")
                except Exception:
                    print("📜 Історія порожня.")
                continue
            
            # ============================================================
            # Відправляємо запит агенту
            # ============================================================*
            print("\\n🤔 Агент думає...")
            
            result = graph.invoke(
                {"messages": [HumanMessage(content=user_input)]},
                config
            )
            
            # Отримуємо фінальну відповідь*
            final_message = result["messages"][-1]
            print(f"\\n🤖 Агент: {final_message.content}")
            
        except KeyboardInterrupt:
            print("\\n\\n👋 Сесію перервано. До побачення!")
            break
        except Exception as e:
            print(f"\\n❌ Помилка: {e}")
            print("Спробуйте переформулювати запит.")
# Запуск інтерактивної сесії
run_interactive_session()



Особливості інтерактивного режиму:

1. Унікальний thread_id для кожної сесії: При запуску генерується випадковий ідентифікатор. Всі повідомлення в межах сесії зберігаються під цим ID.

2. Команда /reset: Створює новий thread_id, фактично починаючи «з чистого аркуша». Попередня історія залишається в checkpointer під старим ID, але нова сесія її не бачить.

3. Команда /history: Використовує метод graph.get_state(config) для отримання поточного стану з checkpointer і виводить історію повідомлень.

4. Збереження контексту: Завдяки checkpointer агент «пам'ятає» все, що було сказано в межах сесії, навіть якщо ви закриєте та знову відкриєте ноутбук (поки процес Python працює).



Крок 14. Комплексне тестування

Проводимо систематичне тестування агента на різних типах запитів, щоб переконатися в коректності роботи всіх компонентів.

# КРОК 14. Комплексне тестування
def run_tests():
    test_cases = [
        ("Порахуй 999 + 111", "calculator"),
        ("Скільки буде 1000 / 8?", "calculator"),
        ("(50 + 50) * 3", "calculator"),
        ("Яка сьогодні дата?", "current_datetime"),
        ("Котра зараз година?", "current_datetime"),
        ("Який день тижня?", "current_datetime"),
        ("Що таке машинне навчання?", "knowledge_base"),
        ("Що таке RAG?", "knowledge_base"),
        ("Привіт! Як справи?", None),
        ("Що ти вмієш?", None),
    ]
    passed = warnings = failed = 0
    print("\n" + "="*60 + "\n🧪 КОМПЛЕКСНЕ ТЕСТУВАННЯ\n" + "="*60)
    for i, (query, expected_tool) in enumerate(test_cases, 1):
        print(f"\n--- Тест #{i} ---\n👤 {query}")
        try:
            config = {"configurable": {"thread_id": f"test-{i}"}}
            result = graph.invoke({"messages": [HumanMessage(content=query)]}, config)
            msgs = result["messages"]
            tool_called = any(isinstance(m, ToolMessage) for m in msgs)
            ans = msgs[-1].content
            if expected_tool:
                status = "✅" if tool_called else "⚠️ tool не викликано"
            else:
                status = "✅" if not tool_called else "⚠️ зайвий tool"
            if "✅" in status: passed += 1
            else: warnings += 1
            print(f"🤖 {str(ans)[:60]}\n📊 {status}")
        except Exception as e:
            print(f"❌ {e}"); failed += 1
    total = len(test_cases)
    print(f"\n{'='*60}\n📊 Результат: ✅{passed} ⚠️{warnings} ❌{failed} ({(passed+warnings)/total*100:.0f}%)\n{'='*60}")


run_tests()



Що перевіряє тестування:

1. Правильність вибору інструменту: Для математичних запитів має викликатися calculator, для запитів про час — current_datetime, для фактологічних — wikipedia_search.

2. Відсутність зайвих викликів: Для звичайних діалогових запитів інструменти не повинні викликатися.

3. Коректність відповідей: Агент має давати осмислені відповіді, використовуючи результати інструментів.
