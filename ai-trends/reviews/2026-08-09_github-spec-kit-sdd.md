# Spec-Driven Development з GitHub Spec Kit: від вайб-кодингу до постановки задач

## Джерело

YouTube, канал FWDS ("вітчийдушний програміст"), відео про перехід від
фрістайл-вайб-кодингу до Spec-Driven Development (SDD) на прикладі
фреймворку GitHub Spec Kit і Claude Code. Дата перегляду: 2026-08-09.

## Резюме

- **Проблеми вайб-кодингу**, названі автором: "прокляття знань" при
  постановці задачі (те, що очевидне автору, не проговорюється), ІІ
  додумує недомовлене, немає формального критерію готовності, контекст
  прийнятих рішень губиться в чаті і не відновлюється пізніше. При
  зростанні проєкту система "розсипається" без задокументованої причини.
- **SDD-підхід:** замість прямого кодингу - ланцюжок артефактів-файлів:
  специфікація (бізнес-вимоги, user story, acceptance criteria) → план
  (технічна реалізація, стек, модель даних, контракти) → задачі
  (детальний breakdown) → імплементація (код). Кожен крок фіксується
  файлом у репозиторії і комітиться разом із кодом.
- **Інструмент:** GitHub Spec Kit, CLI `specify`, слеш-команди
  `/specify`, `/plan`, `/tasks`, `/implement` всередині Claude Code.
  Артефакти складаються в `specs/NNN-slug/` (spec.md, plan.md, tasks.md).
- **Практична порада:** розділяти контексти - чорнову фазу (спека/план/
  таски) вести в одній сесії, а імплементацію запускати в новій сесії,
  дешевшою моделлю (автор перемкнувся на Sonnet, medium effort).
- **Організаційна ідея:** розділення ролей - спеку пише продуктова
  людина, план - технічна, `/implement` може запустити будь-хто. QA може
  паралельно писати тест-кейси по спеці ще до готовності коду.
- **Спекулятивна теза наприкінці:** документація/спека може стати
  "вихідним кодом", а сам код - похідним, генерованим артефактом. Автор
  подає це як гіпотезу, не як факт.

## Факт-чек

- **Spec Kit - продукт GitHub (дочірньої компанії Microsoft)** -
  підтверджено. Репозиторій `github/spec-kit`, ліцензія MIT.
- **"100 тисяч зірочок" на репозиторії** - підтверджено, правдоподібно.
  За даними пошуку станом на липень 2026 - близько 120 тис. зірок, з
  ростом від ~90 тис. у травні 2026. 100 тис. на момент запису відео
  цілком реалістично.
- **Команди `specify init`, `/specify`, `/plan`, `/tasks`, `/implement`**
  - підтверджено, збігається з офіційною документацією
  (github.github.io/spec-kit).
- **Workflow створює ланцюжок файлів spec → plan → tasks у
  `specs/NNN-slug/`** - підтверджено, відповідає офіційному опису.
- **Неповнота демонстрації:** повний офіційний workflow -
  `/constitution → /specify → /clarify → /plan → /tasks → /implement`.
  Автор пропустив кроки `/constitution` (базові принципи проєкту) і
  `/clarify` (уточнювальні питання перед планом) - не помилка, але не
  повний показ можливостей інструменту.
- **Теза "спека стане вихідним кодом, код - похідним"** - не
  перевіряється, чітко подана автором як гіпотеза, а не факт.

## Актуальність

Дата перевірки: 2026-08-09, через веб-пошук. Тема свіжа й активно
розвивається - Spec Kit росте протягом усього 2026 року, напрям у
цілому збігається зі ширшим трендом індустрії на структурований
agentic-кодинг (аналогічний підхід розвиває, наприклад, Kiro AI).

## Зв'язок з навчанням

Пряме перетинання з Tier 2 AI Fundamentals і особливо з capstone-проєктом
StudyMate: у власній роботі вже є патерн "архітектурне рішення →
документація → код" (наприклад, ДЗ8 про поріг схожості 0.55 як
архітектурне, а не промпт-рішення). SDD - формалізація саме цієї
практики. Також перетинається з наступною темою Tier 2 - MLOps CI/CD, де
типово потрібна документована трасованість рішень.

## Зв'язок з ERC

Пряме застосування до ролі PM в ERC. У `erc-work/tasks/` вже є подібний
патерн, але для простих детермінованих задач без ІІ. SDD-підхід
корисніший для більших концептуальних проєктів зі списку
`erc-work/context.md`, які ще на стадії "концепція/планування" -
насамперед **IT support-бот** і **бот з юридичної документації**: обом
потрібна формалізація вимог до початку розробки і трасованість рішень
(наприклад, хто і чому вирішив обмежити бота лише базою документів).

## Висновок

Застосовувати частково. Ядро ідеї - формалізовані вимоги до коду
знижують хаос - здорове і не нове саме по собі, але тепер ІІ сам пише
спеку за коротким брифом, що знижує вартість формалізації. Конкретно
корисне: сам патерн "спека → план → таски → імплементація" як чекліст
постановки задач для проєктів ERC, незалежно від конкретного інструменту;
порада розділяти контексти і переходити на дешевшу модель для
імплементації. Спекулятивна теза про спеку як майбутній "вихідний код" -
цікава, але не факт, до застосування не готова.

Практичний висновок для власної роботи: підхід варто застосовувати при
проєктуванні нових проєктів (не для дрібних правок) - зафіксовано окремо
в AI Auditor (`RULES.md`, розділ 13), щоб рекомендація спливала
автоматично на старті нового проєкту, а не лише коли згадав про це
відео.
