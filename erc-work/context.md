# ERC — контекст для мосту курс↔робота

## Компанія

**ERC** (erc.ua) — міжнародний дистриб'юторський холдинг. Реєстрація —
Відень (Австрія), операційна компанія — Україна, торгові компанії —
декілька країн.

## Моя роль

Product/Project Manager в IT-департаменті. Веду розробку внутрішньої ERP-системи
обліку.

## Технологічний стек

Робоча інфраструктура ERC побудована на продуктах Microsoft: **Microsoft SQL
Server** як основна база даних, **Azure DevOps** для розробки й репозиторіїв,
фронтенд на **JavaScript**. Записано зі слів, за фактом не звірено з
документацією, при потребі уточнити деталі окремо (версія SQL Server,
хмара чи on-premise, конкретний JS-фреймворк на фронтенді).

Враховувати цей стек при виборі інструментів для проєктів зі списку нижче:
за інших рівних варіантів перевагу мають рішення, що добре стикуються з
Microsoft SQL Server і Azure (наприклад, `pgvector`-аналог для MS SQL,
Azure-native векторний пошук, чи self-hosted рішення без залежності від
чужого стека), а не рішення, що тягнуть за собою окрему нетипову
інфраструктуру.

## Головна мета цього файлу і всього мосту курс↔робота

Це не додатковий, а основний сенс усього репозиторію. Дві мети одночасно,
рівнозначні:

1. Допомагати освоювати матеріал курсу.
2. Для кожної пройденої теми свідомо шукати застосування в реальному житті і
   на моїй роботі в ERC.

Список нижче — **не фіксований набір із трьох пунктів, а список, що росте**.
Нові кандидати з'являються по ходу роботи і навчання, докидаються сюди окремим
пунктом зі статусом. Не перезаписувати список як "остаточний" — актуалізувати.

## Реальні AI-проєкти (статус на 30.07.2026)

### Концепція / планування

1. **IT support-бот** для внутрішніх процесів (1000+ співробітників).
2. **Інструмент автоматизації аналізу даних** для комерційного/економічного
   департаментів. Рекомендації до врахування при проєктуванні — див.
   [recommendations.md, пункт 2](recommendations.md#пункт-2-інструмент-автоматизації-аналізу-даних).
3. **Бот з юридичної документації**, суворо обмежений існуючою документацією
   (без вигадування норм, які не підтверджені текстом документа).
4. **Нормалізація кодування/алфавіту в описах товарів.** Проблема: в описах
   товарів символи візуально однакові, але з різних алфавітів (кирилиця
   українська/російська, латиниця — homoglyph-проблема, наприклад "а"
   латинська і "а" кирилична виглядають ідентично, але це різні коди
   символів). Потрібен інструмент, що приводить весь текст до єдиного
   узгодженого алфавіту/кодування. Конкретна задача (~1000+ рядків, перевірка
   змішаного алфавіту по колонках укр/рос/англ) — див.
   [tasks/2026-07-30_normalizatsiya-alfavitu-tovariv.md](tasks/2026-07-30_normalizatsiya-alfavitu-tovariv.md).
5. **Розпізнавання файлів у великих обсягах (PDF).** Масове розпізнавання і
   структурування даних з PDF-документів. Підхід реалізації ще не визначено
   (OCR, layout-parsing, LLM-екстракція — обирати після уточнення вхідних
   даних і обсягу).
7. **MCP-сервер над B2B-порталом замовлень (ідея 06.09.2026).** У нас є
   B2B-портал: клієнт логіниться своїм логіном/паролем, бачить свій
   асортимент (не всі товари, а тільки ті, що йому відкриті), оформлює
   замовлення. Ідея: дати MCP-сервер поверх наявного внутрішнього API
   порталу, щоб клієнт міг оформити замовлення через свого ІІ-агента
   природною мовою, а не тільки через UI сайту. Це не заміна API, а ще один
   спосіб доступу до нього, розрахований саме на ІІ-агентів (детальніше про
   різницю MCP/API — розбирали в навчальному курсі
   [Anthropic Academy, backlog.md #1](../to-learn/backlog.md)). Статус:
   чиста концепція, ще не спроєктовано. Ключові відкриті питання перед
   проєктуванням: як розмежувати авторизацію (у кожного клієнта свій
   логін/пароль, MCP-сервер публічний, отже потрібен OAuth чи токени per
   client, а не спільний ключ), і як убезпечити сам інструмент оформлення
   замовлення від помилкового/вигаданого замовлення (підтвердження перед
   фактичним створенням ордера, звірка товару і ціни з довідником, а не
   довіра тому, що написав агент).

### Вже реалізовано

6. **Розпізнавання нарад (митингів).** Проєкт вже впроваджено в роботі, але є
   нюанси і обмеження, які ще будуть описані окремо (не вигадувати деталі
   заздалегідь, чекати уточнення). Рекомендації до врахування при наступній
   модернізації — див.
   [recommendations.md, пункт 6](recommendations.md#пункт-6-розпізнавання-нарад-митингів).

Перші три (1-3) побудовані на тому ж принципі, що й
[Capstone-проєкт StudyMate](../capstone-studymate/README.md):
**«відповідає тільки на основі бази знань»** — жодних відповідей поза
завантаженою документацією/базою. Для проєктів 4-6 цей принцип не завжди
застосовний напряму (наприклад, нормалізація тексту — детермінована
трансформація, а не генерація відповіді) — не тягнути шаблон штучно туди, де
він не підходить.

## Як користуватись папкою `tasks/`

Коли з'являється реальна робоча задача в ERC , яку можна (повністю або
частково) розв'язати за допомогою ШІ — вона докидається сюди окремим файлом:

```
tasks/YYYY-MM-DD_коротка-назва.md
```

Мінімальна структура файлу задачі:

```markdown
# Назва задачі

## Контекст
Що за задача, хто ставить, який дедлайн.

## Зв'язок з курсом
Яка тема/ДЗ з навчання сюди застосовна.

## Рішення / підхід
Що зроблено, які інструменти, чому саме так.

## Результат
Що вийшло, що не спрацювало, чого варто уникати наступного разу.
```

Це дає змогу питати ІІ-асистента напряму: «ми вивчили тему X, як мені
застосувати її до задачі Y з ERC?» — і отримувати відповідь, що спирається на
реальний контекст роботи, а не на абстрактний приклад.
